**상태**: 코드 수정과 로컬 검증 완료 · 운영 반영 및 재측정 대기 (2026-08-11)

이 문서는 갱신 경로 조사에서 확인한 문제, 이번에 코드로 고친 것, 아직 운영에서 해야 할 일을
한곳에 기록한다. 기준 커밋은 `c544213`, 기준 실행은 GitHub Actions run `31491773531`이다.

운영 R2와 GitHub Actions는 이번 코드 수정 중 건드리지 않았다. 따라서 조사 중 발생한 R2의 하루치

## 1. 수정 전 기준선

| 구간 | 실측 |
|---|---:|
| 갱신 버튼 → workflow 완료 | 111초 |
| 러너 준비 | 18.1초 |
| 수집 | 80.6초 |
| 업로드 | 7.9초 |
| 마무리 | 4.4초 |
| 정상 실행의 전체 HTTP 요청 | 약 45~47회 |
| 최근 일별 CSV 브라우저 캐시 | 최대 300초 |

111초는 현행 구성의 성공 표본 한 건이다. 장기 중앙값으로 사용하지 않는다. 수집이 80.6초로 가장
길지만 요청별 시간이 없었기 때문에 국내 러너, 페이지 크기, 동시성 중 무엇이 유효한지는 판단할 수
없었다. 화면에서는 workflow가 끝나도 같은 CSV URL의 fresh 캐시를 다시 사용해 새 행 반영이 더
늦어질 수 있었다.

## 2. 이번에 완료한 것

### 2.1. 갱신 뒤 브라우저 캐시 재검증

- `public/app.js`가 갱신 완료 직후 현재 조회 대상으로 선택된 최근 일별 CSV에 한해
  `cache: "no-cache"`를 사용한다.
- URL에 캐시버스트 쿼리를 붙이지 않는다. 기존 ETag를 이용해 바뀌지 않은 파일은 304로 처리한다.
- 브라우저를 닫았다가 다시 열어도 `index.updatedAt`이 이전 값과 달라졌으면 첫 조회에서 같은
  재검증을 수행한다.
- workflow 시작 뒤 60초까지는 5초, 그 이후에는 2초 간격으로 상태를 확인한다.

관련 파일: `public/app.js`, `public/search-worker.js`, `public/rows.js`

### 2.2. CSV 바이트 결정성 확보

- `collector/collector.js`가 CSV를 쓰기 전에 행을 공고 키로 정렬한다.
- HTTP 작업 완료 순서가 달라도 같은 데이터는 같은 행 순서와 같은 gzip 바이트를 만든다.
- 업로더의 MD5/ETag 비교가 순서 변화만으로 파일을 변경으로 판정하던 원인을 제거했다.

### 2.3. 요청별 계측 추가

- collector가 각 attempt마다 다음 JSON 로그를 남긴다.

```json
{
  "mode": "bid",
  "type": "물품",
  "range": "2026-07-07~2026-08-03",
  "page": 1,
  "queueWaitMs": 0.2,
  "fetchMs": 1840.3,
  "status": 200,
  "bytes": 123456,
  "retry": 0,
  "upstreamMs": 510.4
}
```

- URL에는 `ServiceKey`가 있으므로 로그에 URL을 남기지 않는다. `mode/type/range/page`만 남긴다.
- Worker 중계는 `Server-Timing: upstream;dur=...`를 반환하고 collector가 이를 `upstreamMs`로
  기록한다.
- collector의 `fetchMs`는 응답 본문을 모두 읽는 시간까지 포함한다. `upstreamMs`는 Worker가
  상류 응답을 받기까지의 시간이다. 두 값을 같은 구간으로 간주해 단순 차감하지 않는다.

관련 파일: `collector/collector.js`, `src/worker.js`

### 2.4. 재시도와 timeout 보강

- 각 요청 attempt에 90초 timeout을 적용했다. 이 시한은 본문을 다 받는 시간까지 포함한다.
  본공고 한 페이지가 5~6MB라 동시 8요청에서는 정상 응답도 15~30초가 걸린다.
- 재시도 여부는 응답 상태가 아니라 오류에 달린 `httpStatus`로 가린다. 상태로 가리면 본문을
  받다 끊긴 요청이 재시도에서 빠진다 — 그때는 헤더에서 읽은 200이 이미 기록돼 있다.
- 408, 429, 5xx는 재시도한다. 인증 오류 같은 다른 4xx는 즉시 실패한다. 상태까지 가지 못했거나
  본문에서 끊긴 실패(네트워크 오류, timeout, 잘린 JSON)는 모두 재시도한다.
- 재시도 대기에는 exponential backoff와 jitter를 적용한다.
- 상류의 `Retry-After`가 있으면 Worker가 전달하고 collector가 그 시간보다 빨리 재시도하지 않는다.
- backoff 중에는 HTTP 동시성 permit을 반환한다. 실패한 한 요청이 잠든 동안 다른 첫 요청을
  막지 않는다.

### 2.5. `--no-resume` 행 제거와 저장 겹치기 수정

- 새 raw 레코드에 ServiceKey와 쿼리를 제외한 `__sourceEndpoint`를 저장한다.
- `--no-resume` 재수집 시 `bsnsDivNm`이 아니라 원천 endpoint를 기준으로 기존 행을 제거한다.
- endpoint 표식이 없던 과거 본공고는 같은 모드·범위의 네 업무 endpoint가 모두 성공한 경우에만
  정리한다. 일부 endpoint가 실패하면 기존 행을 보존한다.
- `--no-resume`에서도 8개 작업마다 중간 저장을 시작해 gzip·파일 쓰기와 남은 HTTP 요청을
  겹친다.

### 2.6. 업로더를 fail-safe 기본값으로 전환

- `node uploader/upload.js`와 `npm run upload`는 이제 항상 dry-run이다.
- 실제 R2 PUT/DELETE는 정확한 `--commit`이 있을 때만 수행한다.
- 알 수 없는 인자와 `--dry-run --commit` 동시 사용은 오류로 끝낸다.
- 실제 실행은 npm의 인자 전달을 거치지 않고 아래처럼 직접 호출한다.

```powershell
node uploader/upload.js --commit
```

GitHub Actions도 같은 명령을 명시적으로 사용한다. 조사 중처럼 npm이 `--dry-run`을 삼켜 실제
삭제 경로로 들어가는 사고는 기본값 단계에서 차단된다.

관련 파일: `uploader/upload.js`, `.github/workflows/collect.yml`, `README.md`

### 2.7. 러너 준비 경로 수정

- Actions의 Node 버전을 20에서 러너 tool cache에 있는 22로 변경했다.
- dev 패키지 tarball이 포함된 기존 setup-node npm 캐시를 복원하지 않는다.
- 외부 패키지를 쓰지 않는 collector를 먼저 실행하고, 성공 확인 뒤 uploader 직전에
  `npm ci --omit=dev`를 실행한다.
- 기본 수집 범위의 의미를 “오늘과 이전 35일”, 양끝 포함 36개 날짜로 문서와 workflow 입력
  설명에 명시했다.

## 4. 아직 하지 않은 것

다음 항목은 코드만으로 완료 판정할 수 없거나, 계측 결과를 먼저 봐야 하므로 남겨 두었다.

- 현재 로컬 변경을 커밋하고 `dev`에 push하지 않았다.
- Worker를 운영 배포하지 않았다.
- 조사 중 하루치 되감긴 R2를 복구할 collect workflow를 실행하지 않았다.
- 수정 후 같은 범위를 연속 두 번 수집해 두 번째 실행의 데이터 PUT 수를 확인하지 않았다.
- Node 22와 npm 캐시 제거 뒤 러너 준비 시간이 실제로 얼마나 줄었는지 측정하지 않았다.
- 페이지별 latency/bytes 분포를 아직 얻지 않았다. 계측 코드만 추가된 상태다.
- `numOfRows`를 999보다 늘리지 않았다.
- `concurrency`를 8보다 늘리지 않았다.
- 국내 러너 또는 별도 VM으로 옮기지 않았다.
- Cloudflare 대시보드의 Cache Rule/Browser TTL override는 확인하지 못했다.
- 나라장터의 최대 `numOfRows`, 28일 초과 범위 완전성, 429 정책은 확인하지 않았다.

## 5. 운영 반영 순서

순서를 바꾸지 않는다. Worker와 Actions 코드가 함께 바뀌므로 반쪽만 반영하면 계측이 빠지거나
구 워크플로가 안전장치 없는 업로더를 실행할 수 있다.

1. 변경 diff와 테스트 결과를 검토하고 한 커밋으로 만든다.
2. `dev`에 push해 collect workflow가 Node 22와 `--commit` 명령을 사용하게 한다.
3. Worker를 배포한다. 이 단계에서 브라우저 재검증 코드와 `Server-Timing`이 운영에 들어간다.
4. collect workflow를 한 번 수동 실행한다. 이것이 조사 중 되감긴 최근 35일 데이터를 복구한다.
5. workflow 성공, `sync-errors.json` 0건, R2 `index.json.updatedAt` 갱신을 확인한다.
6. 브라우저에서 갱신 완료 직후 현재 결과가 다시 조회되는지 확인한다.
7. 동일한 begin/end로 한 번 더 실행해 안정 정렬 뒤 불필요한 데이터 PUT 수를 측정한다.

운영 반영 전에 다시 실행할 안전 검증:

```powershell
npm test
npx wrangler deploy --dry-run
npm run upload
```

마지막 `npm run upload`는 dry-run이다. 출력의 업로드·삭제 예정 수가 예상과 다르면
`--commit`을 실행하지 않는다.

## 6. 운영 확인 기준

### 6.1. R2 복구

- collect workflow가 성공한다.
- `data/sync-errors.json`의 배열 길이가 0이다.
- R2의 `index.json.updatedAt`이 복구 실행 시각으로 바뀐다.
- 2026-08-11 정상 실행 직전과 비교해 최근 35일의 파일과 행이 다시 들어온다.
- 버킷의 과거 월별 봉인 파일이 유지된다.

### 6.2. 브라우저 캐시

- 갱신 완료 뒤 별도 검색 버튼 조작 없이 현재 결과 조회가 다시 실행된다.
- 최근 CSV 요청은 같은 URL을 사용한다.
- 바뀌지 않은 파일은 가능한 경우 304, 바뀐 파일은 200으로 최신 본문을 받는다.
- 갱신 뒤 새 행이 300초 TTL 만료를 기다리지 않고 화면에 나타난다.

### 6.3. 결정적 CSV와 업로드

- 같은 begin/end를 연속 실행했을 때 두 번째 실행의 데이터 PUT가 첫 실행보다 크게 줄어야 한다.
- 두 실행 사이 실제 공고 변경이 없으면 두 번째 PUT는 0에 가까워야 한다.
- PUT가 계속 많으면 변경된 파일 하나를 골라 raw CSV의 행 순서가 아니라 컬럼 순서나 실제 값이
  달라졌는지 비교한다.

### 6.4. 요청 latency

한 번의 정상 실행 로그에서 다음을 집계한다.

| 지표 | 판단에 쓰는 곳 |
|---|---|
| `fetchMs` 중앙값, p90, 최대 | 요청 자체가 느린지 확인 |
| `queueWaitMs` 중앙값, p90, 최대 | 동시성 8이 실제 병목인지 확인 |
| `upstreamMs`와 `fetchMs` 분포 | Worker 상류 구간과 전체 수신 시간 비교 |
| mode/type별 페이지 수와 bytes | `numOfRows` 확대 후보 선정 |
| status와 retry 횟수 | 429/5xx 및 재시도 정책 확인 |

판정 원칙:

- `queueWaitMs`가 작고 `fetchMs`가 크면 동시성을 먼저 올리지 않는다.
- 페이지마다 고정 지연이 크고 응답 bytes가 작으면 `numOfRows` 확대 A/B를 검토한다.
- `upstreamMs`가 대부분을 차지하면 collector 실행 지역보다 Worker→나라장터 구간이 우선이다.
- Worker 밖의 시간이 크고 지역별 차이가 확인되면 그때 국내 러너/VM을 검토한다.
- 429 또는 5xx가 생기면 동시성과 페이지 크기를 높이지 않는다.

## 7. 다음 결정

운영 반영 직후에는 최적화 값을 더 바꾸지 않는다. 먼저 수정된 구성으로 두 번 측정한다.

1. 첫 실행: R2 복구와 새 계측 수집.
2. 같은 범위의 두 번째 실행: CSV 결정성과 불필요한 PUT 제거 확인.
3. 두 실행의 로그를 기준으로 `numOfRows`, `concurrency`, 러너 위치 중 하나만 선택해 A/B한다.

절감치는 서로 겹치므로 여러 값을 동시에 바꾸거나 추정 절감치를 합산하지 않는다.

# 2부. 이슈: GitHub Actions에서 나라장터 API에 연결되지 않는다

**상태**: 해결 (2026-08-10) · **조치**: Worker 중계 경유 · **영향 기간**: 2026-08-09 ~ 08-10

GitHub 러너가 공공데이터포털에 네트워크로 닿지 못하는 문제였다. 코드·시크릿·권한 문제가
아니었다. 아래 3절의 원인 추정은 **범위가 틀렸고**, 4절 아래에 정정과 조치를 적었다.

수집기의 요청만 Cloudflare Worker가 대신 내보내는 것으로 해결했다. 절차는
[README의 "공공데이터 API 중계"](../README.md#공공데이터-api-중계)에 있다.

## 1. 증상

조회 화면에서 **보유데이터 갱신** 버튼을 누르면 다음이 표시된다.

```
갱신 실패: GitHub Actions가 failure 상태로 끝났습니다.
```

워크플로는 정상적으로 디스패치되고 실행되지만, `수집` 스텝에서 모든 작업이 실패한다.

## 2. 근거

하루치(2026-08-09)만 지정해 돌린 진단 실행(run `31291062925`)의 로그다.

```text
fetch failed (UND_ERR_CONNECT_TIMEOUT: Connect Timeout Error
              (attempted address: apis.data.go.kr:443, timeout: 10000ms))
```

| 실행 | 범위 | 결과 |
|---|---|---|
| `31290852961` | 최근 35일 (16개 작업) | **16/16 실패**, 저장 0건 |
| `31291062925` | 하루 (8개 작업) | **8/8 실패**, 저장 0건 |

전부 같은 오류다. 일부 실패나 간헐적 오류가 아니라 **연결이 한 번도 성립하지 않는다.**

## 3. 원인

`apis.data.go.kr:443`으로의 TCP 연결이 10초 안에 완료되지 않는다.

주목할 점은 연결이 **거부**(`ECONNREFUSED`)된 것이 아니라 **타임아웃**이라는 것이다. 서버가
포트를 닫았다면 즉시 거부가 온다. 응답 없이 시간만 흐르는 것은 패킷이 조용히 버려진다는
뜻이고, 방화벽이 특정 대역을 차단할 때 나타나는 형태다.

GitHub 호스티드 러너는 해외(주로 미국 Azure) 대역에서 돈다. 같은 코드가 국내 로컬에서는
정상 동작한다. **공공데이터포털이 해외 IP를 차단하고 있다**는 것이 당시의 해석이었다.

> 이 마지막 문장은 관측(해외에서 타임아웃 / 국내에서 정상)에서 끌어낸 추정이었다.
> 뒤의 4.5절 측정으로 국가 기준이 아니라 IP 대역 기준임을 확인했다.

## 4. 진단 과정에서 걷어낸 것들

같은 "갱신 실패"로 보였지만 원인이 세 번 바뀌었다.

| # | 표시된 메시지 | 실제 원인 | 조치 |
|---|---|---|---|
| 1 | "갱신 API가 없습니다" | 워크플로 파일이 원격에 없었다. `origin/dev`·`origin/main` 어디에도 없어 GitHub이 404를 반환 | `dev` 푸시 + 기본 브랜치를 `dev`로 변경 |
| 2 | Actions failure (19초) | Actions 저장소 시크릿 미등록. 로그에 `SERVICE_KEY:`가 빈 값으로 찍혔다 | 필요한 Actions 시크릿 등록 |
| 3 | Actions failure (1분 53초) | Azure 대역에서 공공데이터포털 연결 타임아웃 | Worker 중계 적용 |

1번은 GitHub이 준 404를 `public/app.js`가 "갱신 API가 없습니다"로 덮어써서 원인이 가려져
있었다. 지금은 서버 메시지를 우선 표시하도록 고쳤다.

3번도 처음에는 `fetch failed` 한 줄뿐이라 DNS·거부·타임아웃·인증서를 구분할 수 없었다.
`collector/collector.js`의 `withCause`가 `error.cause`의 `code`와 `message`를 붙이도록
바꾼 뒤에야 위 로그가 나왔다.

## 4.5. 원인 정정 — 국가가 아니라 IP 대역이다

위 3절은 "공공데이터포털이 해외 IP를 차단한다"로 끝냈다. 측정해 보니 **범위가 틀렸다.**

Cloudflare Worker를 실제 엣지에 올려(`wrangler dev --remote`) 같은 주소를 불렀다.

```text
colo=LAX  country=KR  ok=true  status=403  155~515ms  (4회 연속)
"SERVICE_KEY_IS_NOT_REGISTERED_ERROR" — 키를 test로 넣어서 나온 정상 응답
```

**미국 로스앤젤레스에서 나갔는데 닿았다.** 국가 기준이라면 여기서도 막혔어야 한다.
막힌 것은 GitHub 러너가 쓰는 Azure 대역이고, Cloudflare 대역은 아니다.

| 출발지 | connect | 결과 |
|---|---|---|
| 국내 로컬 | 0.033초 | 응답 도착 |
| GitHub Actions (Azure US) | 10초 초과 | `UND_ERR_CONNECT_TIMEOUT` |
| Cloudflare Worker (LAX) | 0.15~0.52초 | 응답 도착 |

## 5. 조치 — Worker 중계

5절에 적었던 선택지(자체 러너·국내 VM·프록시)는 전부 "국내에 상시 실행 환경을 둔다"는
전제 위에 있었다. 위 측정으로 그 전제가 필요 없어졌다. 이미 돌고 있는 Worker에 중계
경로를 하나 더 여는 것으로 끝난다. 새 인프라도, 켜 두어야 할 PC도 없다.

```text
수집기(러너) --Bearer RELAY_TOKEN--> Worker /api/relay --> apis.data.go.kr
```

`API_BASE`가 비어 있으면 수집기는 종전대로 직접 호출한다. 국내 로컬은 아무것도 바뀌지 않는다.

중계는 경로 화이트리스트(`src/worker.js`의 `RELAY_ALLOW`)와 기계용 토큰으로 제한한다.
전자가 없으면 이 Worker가 공개 프록시가 되고, 후자를 조회 화면의 비밀번호 게이트와
합치면 러너에 로그인 화면이 돌아간다.

검증: 수집기 12개 작업(사전공고·본공고·발주계획 × 4업무)이 중계를 타고 **실패 0건**으로
끝났다. 토큰 없음/오류는 401, 화이트리스트 밖 경로는 403, POST는 405이며, 조회 화면의
게이트는 영향을 받지 않는다(`/`·`/data/`는 그대로 401).

### 자체 러너를 택하지 않은 이유

이 저장소는 **공개**다. 공개 저장소에 개인 PC를 자체 러너로 붙이면, 포크 PR로 `pull_request`
트리거를 가진 새 워크플로 파일을 추가하는 경로로 임의 코드가 그 PC에서 돈다. 그 PC에는
`.env`와 R2 키가 있다. 중계 방식에는 이 노출이 없다.

## 5-A. 당시 검토했던 선택지

| 방안 | 되는가 | 대가 |
|---|---|---|
| **자체 러너(self-hosted)를 국내에 둔다** | 가능 | 해당 PC·VM이 켜져 있어야 한다 |
| **수집은 로컬에서, 업로드만 유지한다** | 가능 | 갱신 버튼을 쓸 수 없다 |
| 국내 리전의 서버·함수에서 수집한다 | 가능 | 인프라와 비용이 늘고, Worker가 그쪽을 부르도록 바꿔야 한다 |
| 해외에서 국내로 나가는 프록시를 둔다 | 불확실 | 비용·안정성·이용약관 문제 |

### 당시 권장안: 자체 러너 — 채택하지 않았다

이미 로컬에서 수집 파이프라인을 돌리고 있으므로 같은 환경에 러너를 붙이는 비용이 가장 작다는
판단이었다. 워크플로 수정은 `runs-on`을 바꾸는 정도다.

```yaml
jobs:
  collect:
    runs-on: self-hosted    # ubuntu-latest에서 변경
```

이 경우 갱신 버튼이 설계대로 끝까지 동작한다. 대신 러너가 꺼져 있으면 실행이 큐에 쌓인다.
현재는 5절의 Worker 중계를 채택했으므로 적용하지 않는다.

### 대안: 수집을 로컬에 남긴다

갱신 버튼을 제거하거나 비활성으로 두고 사람이 다음을 실행하는 대안이다.

```powershell
npm run collect
node uploader/upload.js --commit
```

`src/worker.js`의 `/api/refresh`와 `GITHUB_TOKEN` 시크릿은 이 경우 필요 없어진다.

## 6. 크론

조사 중에 껐다면 시크릿(`API_BASE`·`RELAY_TOKEN`)을 등록하고 배포한 **뒤에** 되살린다.

```powershell
gh workflow enable collect.yml --repo tkddls8848/gong-go
```

`API_BASE`가 비어 있으면 러너가 직접 호출로 되돌아가 같은 타임아웃이 재현된다.

## 7. 이 이슈와 무관하게 정상인 것

원인을 좁히는 과정에서 아래는 실제 요청으로 확인했다.

- Worker 배포(`56c126ed`)와 게이트 — 미인증 시 정적 자산·R2·없는 경로 모두 401
- 갱신 버튼의 디스패치와 상태 폴링 — GitHub 실행이 시작되고 결과가 화면에 돌아온다
- 필요한 Actions·Cloudflare 시크릿과 Worker/Actions 사이의 `RELAY_TOKEN` 일치
- 워크플로 등록 — `gh workflow list`에 `collect` / id `330281485` / active
- 액션 v7 승격 후 런타임 강제 실행 경고 해소

즉 **공공데이터포털이 허용하는 대역에서 API 요청을 대신 내보내면 전체가 이어진다.**

# 3부. 앞으로 추가할 기능

코드에 "나중에 쓰려고" 열어 둔 자리들이 있었다. 부르는 곳이 생기지 않은 채 남아 공개 표면만
넓히고 있어 `5bb8bdf`에서 걷어냈다. 무엇을 노린 자리였는지를 여기 옮겨 적는다.
필요해지면 그 커밋을 되짚어 되살리면 된다.

각 항목의 **근거**는 코드가 실제로 말해 주는 것, **추정**은 그 자리를 왜 열어 뒀는지에 대한
해석이다. 둘을 구분해 두었으니 추정 쪽은 그대로 믿지 말고 다시 판단한다.

인용한 줄 번호는 2026-08-09 기준이다. 그 뒤로 `collector/backfill.js`·`slim.js`·
`export-raw.js`가 삭제되고 `src/worker.js`가 크게 바뀌었으니, 손대기 전에 해당 위치를
다시 확인한다.

## 1. 조회 결과 클라이언트 재필터링 — 체감이 가장 크다

**흔적**: `public/app.js`의 `records` 변수. `applyFilters()`가 `records = collected`로 담아
두기만 하고 읽는 곳이 없었다. `filtered = collected.sort(...)`가 제자리 정렬이라 두 변수는
같은 배열을 가리키고 있었다.

**근거**: 지금은 검색 버튼, Enter, 초기화, 모드 전환(사전/본공고), 관심 기관 추가·삭제가
전부 `applyFilters()`를 부른다. 그때마다 구간에 걸친 CSV를 **전부 다시 받아 다시 파싱한다.**
기관 목록 편집은 400ms 디바운스가 걸려 있지만 그래도 편집 한 번에 한 번씩 전체 재수신이다.

**추정**: `records`는 "받아 둔 원본"을, `filtered`는 "거른 결과"를 맡기려던 자리다.

**하려면**: `applyFilters()`를 둘로 나눈다. 날짜 구간과 모드가 그대로면 네트워크를 건너뛰고
메모리의 행만 다시 거른다.

```
현재:  조건 변경 → 구간 CSV 전부 재수신 → 파싱 → 필터 → 렌더
목표:  구간·모드 바뀜  → 재수신 → 파싱 → 캐시에 저장 → 필터 → 렌더
       그 외(검색어·업무구분·기관) → 캐시에서 필터 → 렌더
```

**주의**: 캐시 대상은 조건 검사 **이전**의 행이어야 한다. 파일을 읽는 즉시 조건으로 걸러진
결과만 캐시하면 조건을 넓힐 때 없는 행을 찾게 된다. 또 `MAX_ROWS`가 200,000이라 전량 보관은
메모리를 크게 먹는다. 구간별로 최근 것만 들고 있거나, 캐시 히트 조건을 "같은 구간·같은
모드"로 좁게 잡는다.

## 2. 원본 컬럼 되살리기 — 재수집 없이

**흔적**: `shared/service-columns.js`의 `SERVICE_COLUMNS` export.

**근거**: 파일 머리 주석이 계획을 그대로 적어 두었다. 본공고 원본은 170컬럼인데 서비스가
쓰는 것은 28개뿐이고, 나머지(낙찰방법·담당자 연락처·예산 항목·각종 코드)는 버려서 파일이
약 72% 작아진다. 그러면서 **"나중에 다른 컬럼이 필요해지면 재수집 없이 원본에서 꺼내면
된다"**고 적혀 있다.

**원본이 실제로 있는 곳**: `collector.js`가 일별 파일을 쓸 때마다 원본 전체를 `data/raw/`
아래 같은 구조로 미러링한다. 즉 `data/raw/{pre,bid,plan}/YYYY/MM/DD.csv.gz` 한 벌이 있다.
`compact.js`는 월을 봉인하며 일별 서비스 파일을 지울 때도 `data/raw`를 최후 복구 경로로
남긴다. 업로더도 `data/raw`를 배포 대상에서 제외한다.

**추정**: 화이트리스트를 밖에서 읽을 수 있어야 "지금 무엇을 버리고 있는지" 보여 주거나,
원본에서 특정 컬럼만 꺼내 붙이는 도구를 만들 수 있다.

**하려면**

- `SERVICE_COLUMNS`를 다시 export한다.
- `data/raw/`의 같은 날짜 파일에서 컬럼을 꺼내 서비스 CSV에 붙이는 스크립트를 만든다.
  경로가 1:1 대응이라 파일 단위로 짝을 찾을 수 있고, 행 조인 키는 `bidNtceNo`(본공고),
  `bfSpecRgstNo`(사전공고), `orderPlanUntyNo`(발주계획)다.
- 원본을 한 덩어리로 묶어 주던 `collector/export-raw.js`와 컬럼 축소용 `slim.js`는 이미
  삭제됐다. 필요하면 새로 만들어야 한다.
- 화면에 컬럼 선택 UI를 붙일 거라면, 추가한 컬럼이 R2 재업로드 대상이 된다는 점을 계산에
  넣는다. 봉인된 월 파일을 건드리면 `immutable` 캐시가 1년이라 즉시 반영되지 않는다.

**주의**: `bidNtceNo`/`bfSpecRgstNo`/`orderPlanUntyNo`와 날짜 필드는 collector의 증분 병합
키라 어떤 경우에도 빼면 안 된다.

## 3. HWPX 표를 구조 그대로 쓰기 — ECR 추출 정확도

**흔적**: `converter/hwpx-table.js`의 `tableOf`, `textOf` export.

**근거**: `tableOf(xml, stats)`는 HWPX의 `hp:tr`/`hp:tc`를 훑어 `colSpan`/`rowSpan`을 펼친
2차원 격자를 만든다. 병합 셀을 옆·아래로 복제해 직사각형 격자를 보장한다. 지금은 이 격자가
곧바로 `markdownTable()`로 들어가 Markdown 문자열이 되고, 바깥에는 `hwpxToMarkdown`만
공개된다.

**추정**: 표를 Markdown이 아니라 데이터로 꺼내려던 자리다.

**왜 가치가 있나**: `analyzer`는 ECR 총괄표를 Markdown 텍스트에서 다시 파싱한다. 표를
격자로 바로 받으면 파이프 이스케이프(`\|`)와 줄바꿈 치환(`<br>`)을 거치지 않아 왕복 손실이
없다. `verify.js`가 잡아내는 "세부내용_원문이 변환 Markdown에서 확인되지 않음"류의 오탐도
줄어들 여지가 있다.

**하려면**: `hwpxToMarkdown` 옆에 표 격자를 함께 돌려주는 함수를 두고, analyzer가 Markdown
대신 그것을 먹게 한다. 기존 경로를 바로 갈아엎지 말고 두 결과를 비교하는 단계를 먼저 둔다.

## 4. 인덱스 부분 재생성

**흔적**: `shared/pipeline-utils.js`의 `indexEntry` export.

**근거**: `indexEntry(relative, count)`는 경로 하나로 `{mode, begin, end, path, count}` 항목
하나를 만든다. 월별 봉인 경로면 그 달의 1일~말일 구간으로, 일별이면 `begin === end`로 잡는다.
지금은 `buildIndexEntries(counts)`가 전체를 한 번에 만들 때만 내부에서 쓴다.

**추정**: 인덱스 전체를 다시 만들지 않고 **항목 하나만 고치거나 끼워 넣는** 도구를 위한
자리다. 업로더가 한 파일만 다시 올렸을 때, 또는 인덱스가 깨져 특정 달만 손볼 때 쓸 수 있다.

**주의**: 부분 갱신은 `buildIndexEntries`가 하는 중복 제거를 건너뛴다. 같은 달에 월별 봉인
파일과 일별 파일이 함께 있으면(봉인 직후 `--prune` 전) 월 파일만 남겨야 하고, 안 그러면
프런트가 같은 행을 두 번 읽는다. 부분 갱신 도구를 만들면 이 규칙을 직접 지켜야 한다.

## 5. 첨부 파일명 안전성 검사 공용화

**흔적**: `converter/zip-read.js`의 `isSafePath` export.

**근거**: `isSafePath(name)`은 zip-slip 방어다. 빈 이름, `\` 포함, `/`로 시작, 경로 요소에
`..`가 있는 항목을 거른다. 현재는 `readZip`이 중앙 디렉터리를 훑을 때만 쓴다.

**추정**: 첨부를 디스크에 쓰는 다른 지점(`downloader/`)에서도 같은 규칙을 쓰려던 자리다.

**참고**: `shared/pipeline-utils.js`에 이미 `safeFileName`이 있다. 새로 export하기 전에 둘의
역할이 겹치는지 먼저 본다. 하나로 합치는 편이 나을 수 있다.

## 6. 텍스트 정규화 규칙 공용화

**흔적**: `analyzer/verify.js`의 `normalize` export.

**근거**: `normalize(value)`는 연속 공백을 하나로 접고 앞뒤를 자른다. 추출한
`세부내용_원문`의 앞 40자가 변환 Markdown 안에 있는지 확인할 때 양쪽에 같은 규칙을 적용하는
용도다.

**추정**: 같은 정규화를 다른 비교기에서도 쓰려던 자리다. 공고 중복 탐지, 개정 전후 diff처럼
"공백 차이를 무시하고 같은 문서인지" 보는 기능이 후보다.

**규모**: 한 줄짜리 함수다. 다시 필요해지면 `shared/`로 올리는 편이 낫다.

## 7. 변환 단계 상태 파일

**흔적**: `converter/convert.js`가 `readJson`을 import해 놓고 쓰지 않았다.

**근거**: 같은 파일이 `writeJson`은 실제로 쓴다. 읽기만 짝이 없었다.

**추정**: 변환 결과를 쓰기만 하지 말고 읽어서 **이미 끝난 첨부를 건너뛰는 재개(resume)**를
붙이려던 자리로 보인다. collector에는 이미 `resume` 개념이 있다(`sync.config.json`).

**확실하지 않다**: 근거가 "import만 있었다" 하나뿐이라 추정이 약하다. 변환 재개가 필요한지는
실제 재실행 비용을 재 보고 판단한다. HWP→HWPX 변환은 한글 COM을 타므로 느릴 가능성이 크다.
