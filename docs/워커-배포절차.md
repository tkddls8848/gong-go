# Cloudflare Workers 배포 절차

`dev` 브랜치 뷰어(`src/worker.js` + `wrangler.jsonc`)를 Cloudflare Workers에 올리는 절차다.
Pages에서 Workers로 전환한 배경과 대조 검증 내역은 [workers-전환-보고.md](workers-전환-보고.md),
전체 배포 설계는 [배포계획-R2.md](배포계획-R2.md)를 본다.

## 현재 배포 상태 (2026-08-09 기준)

| 항목 | 값 |
|---|---|
| URL | <https://gong-go-dev.tkddls8848.workers.dev> |
| Worker | `gong-go-dev` |
| 계정 | `tkddls8848@gmail.com` / `6c09816f97a4b08001c4122de4d581bc` |
| 첫 코드 배포 | 2026-08-09, Version `74b7e7dd-2b33-4559-8008-a4d4dff53953` |
| R2 버킷 | `gong-go-data` (2026-08-08 생성) |
| 적재 데이터 | 1,182건 / 72.1MB, `index.json` 285항목 |
| `GATE_PASSWORD` | 등록됨 (`wrangler secret list`로 확인) |

**게이트는 프로덕션에서 동작을 확인했다.** 미인증 상태로 `/`, `/index.html`, `/app.js`,
`/style.css`, `/plan.md`, `/nonexistent` 전부 401 + 로그인 화면이 나온다. 즉
`assets.run_worker_first: true`가 실제로 정적 자산보다 먼저 Worker를 태우고 있다.

아래 절차는 이 배포를 재현하거나 다시 배포할 때 그대로 쓴다.

## 0. 배포되는 것


| 대상        | 출처                                           | 비고                                                 |
| --------- | -------------------------------------------- | -------------------------------------------------- |
| Worker 코드 | `src/worker.js`                              | 게이트 → `/data/**` R2 중계 → 정적 자산 순서                  |
| 정적 자산     | `public/` 전체                                 | `index.html`, `app.js`, `style.css`, **`plan.md`** |
| R2 바인딩    | `wrangler.jsonc`의 `DATA` → 버킷 `gong-go-data` | 코드가 아니라 설정이 선언한다                                   |
| 시크릿       | `GATE_PASSWORD`                              | 파일이 아니라 `wrangler secret put`으로만                   |


데이터(`data/`)는 배포물에 들어가지 않는다. R2에 따로 올리며 Worker가 중계한다.

Worker 이름은 `wrangler.jsonc`의 `name`인 `gong-go-dev`이고, 기본 URL은
`https://gong-go-dev.<계정서브도메인>.workers.dev`가 된다.

## 1. 사전 점검 (계정 없이 가능)

```powershell
npm ci
npm test
npx wrangler deploy --dry-run
```

`--dry-run`의 기대 출력은 다음과 같다. **바인딩 목록에 `DATA`와 `ASSETS` 외의 항목이
보이면 멈춘다** — `.env`의 파이프라인 자격증명이 딸려 들어갔다는 뜻이다.

```text
✨ Read 4 files from the assets directory ...\public
Your Worker has access to the following bindings:
Binding                        Resource
env.DATA (gong-go-data)        R2 Bucket
env.ASSETS                     Assets
```

## 2. 로그인

```powershell
npx wrangler whoami              # 현재 상태 확인
npx wrangler login --device      # 코드를 브라우저에 입력하는 방식
```

`wrangler login`은 브라우저 인증이 필요하므로 에이전트가 대신 실행할 수 없다. 사람이 직접 실행한다.

기본 `wrangler login`은 `localhost:8976` 콜백을 쓰는데, 브라우저에 이전 콜백 URL이 남아 있으면
낡은 `state` 값이 새 세션으로 들어와 실패한다. 실제로 아래 오류를 겪었다.

```text
▲ [WARNING] Received query string parameter doesn't match the one sent!
X [ERROR]
errorType: "ErrorInvalidReturnedStateParam"  ("user oauth invalid returned state")
```

`--device`는 콜백 서버를 아예 쓰지 않으므로 이 문제에 구조적으로 면역이다. 콜백 방식을
고수하려면 브라우저의 `dash.cloudflare.com`·`localhost:8976` 탭을 모두 닫고
`npx wrangler logout` 후 `--callback-port 8977`처럼 포트를 바꿔 재시도한다.

## 3. R2 버킷 준비

```powershell
npx wrangler r2 bucket list
npx wrangler r2 bucket create gong-go-data    # 없을 때만
```

버킷 이름은 세 곳이 같아야 한다.

- `wrangler.jsonc`의 `r2_buckets[0].bucket_name`
- `uploader/upload.js:22`의 기본값
- `.env`의 `R2_BUCKET`(설정한 경우)

**버킷의 Public URL(r2.dev)은 켜지 않는다.** 켜면 게이트를 우회해 데이터에 직접 접근할 수 있다.

## 4. `GATE_PASSWORD` 등록 — 배포보다 먼저

```powershell
npx wrangler secret put GATE_PASSWORD
```

Worker가 아직 없으면 wrangler가 "새 Worker를 만들까?"라고 묻는다. `Y`로 답한다. 이때 만들어지는
것은 **시크릿만 담긴 껍데기**이고 `src/worker.js`는 아직 올라가지 않았다. 이 상태에서
`wrangler deployments status`를 보면 배포 원인이 `Source: Secret Change` 하나뿐이다.
코드는 5단계에서 올라간다.

여기에 넣는 값은 `.env`의 `GATE_PASSWORD`와 **자동으로 같아지지 않는다.** `.env`는 로컬
`wrangler dev`와 devserver용이고, 배포본은 여기 등록한 값만 쓴다. 두 값을 다르게 두면
7단계 검증에서 `.env` 값으로는 계속 401이 나온다. 특별한 이유가 없으면 같은 값으로 맞춘다.

> **순서를 바꾸지 않는다.** `src/worker.js`는 `GATE_PASSWORD`가 비어 있으면 설정 누락으로
> 사이트가 잠기는 사고를 막기 위해 **통과 모드**로 동작한다. 배포를 먼저 하면 시크릿을
> 넣기 전까지 workers.dev URL이 무인증으로 열려 있다.

등록 확인:

```powershell
npx wrangler secret list
```

## 5. 배포

```powershell
npm run deploy      # = wrangler deploy
```

> **`--secrets-file .env`를 붙이지 않는다.** 기본 `wrangler deploy`는 `.env`를 올리지 않지만,
> 이 플래그를 쓰면 `.env`의 `SERVICE_KEY`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`가
> Worker 시크릿으로 업로드된다. 수집 파이프라인 자격증명이라 Worker에 있을 이유가 없다.

성공 출력의 마지막 두 줄이 URL과 버전이다.

```text
Deployed gong-go-dev triggers (0.97 sec)
  https://gong-go-dev.tkddls8848.workers.dev
Current Version ID: 74b7e7dd-2b33-4559-8008-a4d4dff53953
```

함께 나오는 경고 두 개는 실패가 아니라 **암묵적 기본값을 알리는 것**이다.

| 경고 | 기본 동작 | 명시하려면 |
|---|---|---|
| `'workers_dev' is not in your Wrangler file` | workers.dev 주소가 켜진다 | `"workers_dev": true` |
| `'preview_urls' setting is not in your Wrangler file` | 버전별 미리보기 URL이 켜진다 | `"preview_urls": false` |

미리보기 URL은 `<버전>-gong-go-dev...workers.dev` 형태로 **과거 버전까지 접근 가능한 주소를
만든다.** 같은 Worker 코드가 도므로 게이트는 그대로 걸리지만, 노출면을 줄이려면
`wrangler.jsonc`에 `"preview_urls": false`를 명시한다.

## 6. 데이터 업로드

Worker는 R2를 중계할 뿐이므로 버킷이 비어 있으면 화면에 아무것도 나오지 않는다.

> **`npm run collect`로 전체 기간을 받지 않는다.** `collector/sync.config.json`의 `begin`이
> `2020-01-01`이라 한 프로세스에 6년치가 쌓여 V8 힙이 터진다. 여러 해를 받을 때는 분기 단위로
> 순차 실행하는 백필 드라이버를 쓴다(README 참조).

```powershell
# 처음 한 번 — 전체 기간 백필 (분기 단위 순차, 힙 4GB)
node collector/backfill.js --from=2020-01-01 --to=2026-08-02 --heap=4096

# 이후 증분 — 최근 창만 다시 받는다
npm run collect

npm run upload      # 변경분만 R2로 PUT
```

여러 기간을 **병렬로 실행하면 서로의 `index.json`을 지운다.** 반드시 순차로 돌린다.
백필은 분기마다 `data/sync-errors.json`을 확인해 실패 건을 `data/backfill-errors.json`에
모아 두므로, 429·쿼터 초과가 섞였으면 한도 회복 후 같은 명령을 다시 실행하면 실패분만 받는다.

`upload`는 `.env`의 `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`를 쓴다.
토큰은 대상 버킷에 한정된 Object Read & Write 권한만 준다.

## 7. 배포 후 검증

`<URL>`은 배포 출력에 찍힌 workers.dev 주소, `<PW>`는 4단계에서 넣은 값이다.
**`<URL>`·`<PW>`는 자리표시자다.** 그대로 실행하면 `curl: (3) URL rejected: Bad hostname`이 난다.

> **배포 직후 1~2분은 결과를 믿지 않는다.** 실제로 배포 직후에는 `/`와 `/app.js`가
> `404 text/plain`을 반환했고, 잠시 뒤 같은 요청이 정상적으로 401 로그인 화면이 되었다.
> 전파가 끝나기 전의 응답이므로 이상하면 조금 기다렸다 다시 친다.

암호가 셸 기록에 남는 것을 피하려면 아래처럼 입력받아 쓴다.

```powershell
$U = "https://gong-go-dev.tkddls8848.workers.dev"
$PW = Read-Host "GATE_PASSWORD"      # 화면에 남지만 히스토리에는 안 남는다
$H = @{ "X-Gate-Password" = $PW }

# 미인증 — 전부 401이어야 한다
"/","/index.html","/app.js","/style.css","/plan.md" | ForEach-Object {
  "$_ -> " + (Invoke-WebRequest "$U$_" -SkipHttpErrorCheck).StatusCode }

# 인증
(Invoke-WebRequest "$U/" -Headers $H -SkipHttpErrorCheck).StatusCode                 # 200
(Invoke-WebRequest "$U/data/index.json" -Headers $H -SkipHttpErrorCheck).StatusCode  # 200
(Invoke-WebRequest "$U/data/raw/bid/2023/12/11.csv.gz" -Headers $H -SkipHttpErrorCheck).StatusCode  # 404
(Invoke-WebRequest "$U/data/state/sync-state.json" -Headers $H -SkipHttpErrorCheck).StatusCode      # 404
```

curl로 하려면 다음과 같다.

```powershell
curl.exe -i https://<URL>/                                    # 401 + 로그인 화면
curl.exe -i https://<URL>/app.js                              # 401  ← 자산도 게이트 뒤
curl.exe -i -H "X-Gate-Password: <PW>" https://<URL>/         # 200 text/html
curl.exe -i -H "X-Gate-Password: <PW>" https://<URL>/data/raw/bid/2023/12/11.csv.gz    # 404
curl.exe -i -H "X-Gate-Password: <PW>" https://<URL>/data/state/sync-state.json        # 404
curl.exe -i -H "X-Gate-Password: <PW>" https://<URL>/data/index.json                   # 200
curl.exe -I -H "X-Gate-Password: <PW>" https://<URL>/data/pre/2020/01.csv.gz           # 200
```

마지막 응답 헤더에서 확인할 것:


| 항목                 | 기대값                                             | 틀리면                       |
| ------------------ | ----------------------------------------------- | ------------------------- |
| `Content-Type`     | `application/gzip`                              | —                         |
| `Content-Encoding` | **없어야 한다**                                      | 브라우저가 먼저 풀고 프런트가 또 풀어 깨진다 |
| `Cache-Control`    | 과거 월 파일은 `private, max-age=31536000, immutable` | 캐시 정책 확인                  |
| `ETag`             | 있어야 한다                                          | 조건부 요청이 안 먹는다             |


ETag를 그대로 되보내 304를 확인한다.

```powershell
curl.exe -i -H "X-Gate-Password: <PW>" -H 'If-None-Match: "<ETAG>"' https://<URL>/data/pre/2020/01.csv.gz
```

마지막으로 브라우저에서 `https://<URL>/`을 열어 로그인 폼 → 암호 입력 → 조회 화면까지
확인한다. 로그아웃은 `https://<URL>/__gate/logout`이다.

### 프로덕션 실측 (2026-08-09, 첫 배포 직후)

미인증 경로는 전부 통과했다. 게이트가 정적 자산보다 먼저 도는 것이 실제로 확인된 부분이다.

```text
GET /               -> 401 text/html   GET /index.html  -> 401 text/html
GET /app.js         -> 401 text/html   GET /style.css   -> 401 text/html
GET /plan.md        -> 401 text/html   GET /nonexistent -> 401 text/html
GET /data/index.json(미인증) -> 401
응답 헤더: Cache-Control: no-store / Server: cloudflare
```

인증 경로는 **아직 미검증이다.** 배포된 시크릿이 `.env`의 `GATE_PASSWORD`와 달라
`.env` 값으로는 401이 계속 나온다. 실제 암호로 위 PowerShell 블록을 돌려 200/404/304를
확인해야 이 절이 완료된다. 두 값을 맞추려면 `npx wrangler secret put GATE_PASSWORD`로
`.env`와 같은 값을 다시 등록한다.

배포본에서도 같은 값이 나와야 한다.


## 9. 자주 걸리는 것


| 증상                        | 원인                                               | 조치                                      |
| ------------------------- | ------------------------------------------------ | --------------------------------------- |
| 암호 없이 사이트가 열린다            | `GATE_PASSWORD` 미등록 → 통과 모드                      | 4단계                                     |
| `/`는 401인데 `/app.js`가 200 | `assets.run_worker_first`가 꺼졌다                   | `wrangler.jsonc`에서 `true` 유지            |
| `/data/**`가 전부 404        | 버킷이 비었거나 이름 불일치                                  | 3·6단계                                   |
| gzip이 깨져 보인다              | 응답에 `Content-Encoding: gzip`이 붙었다                | Worker가 붙이지 않는지 확인                      |
| 로컬 curl 테스트 결과가 이상하다      | Git Bash의 MSYS 경로 변환이 `/app.js`·`//x` 같은 인자를 바꾼다 | PowerShell에서 실행하거나 `MSYS_NO_PATHCONV=1` |
| `Cannot find module '@aws-sdk/client-s3'` | `node_modules`가 깨졌다(디렉터리는 있는데 `package.json`·`dist-cjs` 없음) | `npm ci` |
| `npm ci`가 `EBUSY ... rmdir miniflare` | 이전 `wrangler dev`의 `node`·`workerd` 프로세스가 살아서 파일을 잡고 있다 | 아래 정리 명령 후 `npm ci` |
| `npm run collect`가 V8 스택을 뱉고 죽는다 | 6년치를 한 프로세스에 쌓아 힙 초과 | 6단계의 `backfill.js` |
| `curl: (3) URL rejected: Bad hostname` | `<URL>`·`<PW>` 자리표시자를 그대로 실행했다 | 배포 출력의 실제 주소로 치환 |
| 배포 직후 `/`가 `404 text/plain` | 전파가 아직 안 끝났다 | 1~2분 뒤 재시도 |
| 올바른 암호인데 계속 401 | 배포 시크릿과 `.env` 값이 다르다 | `wrangler secret put GATE_PASSWORD` 재등록 |
| `wrangler login`이 `ErrorInvalidReturnedStateParam` | 낡은 OAuth 콜백이 끼어들었다 | `--device` 또는 `--callback-port` 변경 |


로컬 검증에 띄운 `wrangler dev`는 터미널을 닫아도 `node`·`workerd` 자식 프로세스가 남는다.
`node_modules`를 잠가 `npm ci`를 막으므로 이렇게 정리한다. MCP나 다른 도구의 `node`는
건드리지 않도록 명령줄로 걸러낸다.

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe' OR Name='workerd.exe'" |
  Where-Object { $_.CommandLine -like '*workerd-windows-64*' -or
                 ($_.CommandLine -like '*wrangler*' -and $_.CommandLine -like '*dev --local*') } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

## 10. 알아 둘 것

- `public/plan.md`(26KB)가 정적 자산으로 함께 배포된다. 게이트 뒤이긴 하지만 암호를 아는
사람에게는 `/plan.md`로 노출된다. 원치 않으면 `public/` 밖으로 옮긴다.
- `assets.run_worker_first: true`라서 정적 자산 요청도 Worker 호출로 계산된다. Pages
`_middleware.js`가 모든 요청보다 먼저 돌던 것과 같은 비용 구조이므로 전환에 따른 회귀는 아니다.
- Workers 무료 한도는 프로젝트가 아니라 **계정 전체**에 걸린다. `main`의 `gong-go` 앱이
아직 Pages Functions로 같은 계정에 떠 있다면 한도를 나눠 쓴다.
- `wrangler.jsonc`에 `observability`가 없어 배포 후 Worker 로그가 남지 않는다. 필요하면
`"observability": { "enabled": true }`를 추가한다.
- 크론(`.github/workflows/collect.yml`)은 저장소에 푸시하지 않으므로 Worker 재배포를
트리거하지 않는다. 코드를 고칠 때만 `npm run deploy`를 다시 돌린다.
