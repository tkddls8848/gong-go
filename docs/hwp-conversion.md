# 브라우저 한글 문서 → PDF

공고 조회의 **HWP·HWPX → PDF 변환** 링크(`/convert.html`)에서 파일을 선택한다.
변환·다운로드에는 AI 잠금 해제가 필요 없다. 사이트 조회용 로그인은 기존대로 필요하다.
문서 내용은 서버, CDN, LLM에 전송하지 않는다. 서버에서 받는 것은 정적 엔진·글꼴뿐이다.
다른 프로그램이나 한글 설치 없이 브라우저에서 실행한다.

ECR 분석 화면에서도 HWP/HWPX를 선택할 수 있다. **분석 실행을 누른 경우** 로컬 변환을 마친
PDF만 기존 `/api/ecr`에 전송한다. 기존 웹 분석은 Cloudflare 경로이며 Ollama로 바뀐 것은 아니다.
로컬 Ollama 이미지 분석에는 이 화면에서 내려받은 PDF를 `analyzer/pdf-pages.py`와
`analyzer/ollama-pdf.js`에 넣는다. [분석 실행 방법](ecr.md#로컬-ollama-pdf-이미지-검증)을 참고한다.

## 구조와 자원

- `public/hwp-converter.js`: 변환 API, 1건 실행, 입력·출력 제한, 90초 제한, 취소.
- `public/hwp-worker.js`: HWP 5 OLE/HWPX ZIP 시그니처 검사, 페이지 검사, Rust/WASM 실행.
- `public/convert-ui.js`·`convert-app.js`: 다운로드 URL 수명과 화면 조립.
- `public/ecr-ui.js`: HWP일 때만 변환을 기다린다. 취소·공고 변경·AI 잠금 후에는 업로드하지 않는다. 공고 첨부에서 받은 HWP도 같은 경로를 탄다. 누락 번호 재분석은 변환한 PDF를 다시 보내므로 다시 변환하지 않는다.
- `public/vendor/hwp-v0.2.2/`: 수정하지 않은 rhwptopdf 배포 자산과 나눔 글꼴, 라이선스.

엔진은 [rhwptopdf v0.2.2](https://github.com/sanguneo/rhwptopdf/releases/tag/v0.2.2)를 사용한다.
Rust로 구현된 파싱·조판·PDF 출력을 WebAssembly로 실행하며, JS는 UI·Worker 통신을 맡는다.
별도 Rust 빌드 환경이 없어도 저장소의 검증된 바이너리로 실행할 수 있다.
엔진·글꼴은 변환 버튼을 눌렀을 때만 로드한다. 관련 자산 총 11,383,082바이트(약 10.86MiB),
파일별 gzip 합계는 약 4.00MiB다. 실제 전송량은 호스팅 압축·캐시 설정에 따라 다르다.
버전 디렉터리는 장기 캐시하며 변경 시 새 경로를 사용해야 한다.
두 글꼴은 나눔고딕·나눔명조의 일반체로, 원본 글꼴을 포함하지 않은 문서에도 대체 글꼴을 제공한다.

문서 버퍼는 transferable로 Worker에 전달한다. 동기 WASM 실행 중에도 메인 화면은 응답하며,
취소·제한 시간 초과·완료 시 Worker를 종료해 WASM 힙과 문서 메모리를 반환한다.
새 작업은 브라우저 HTTP 캐시의 엔진·글꼴을 재사용한다. PDF 다운로드 URL은 다음 작업과 페이지
종료 때 해제한다. 문서 바이트를 localStorage·IndexedDB에 저장하지 않는다.

자산 무결성 검사: `node tools/hwp-assets.cjs`. 누락 자산 복구: `node tools/hwp-assets.cjs --download`.
다운로드한 바이트의 SHA-256이 고정된 값과 일치할 때만 저장한다. 의도적인 버전 변경은 엔진,
글꼴, 라이선스, 해시와 실문서 회귀 검사를 함께 갱신한다.

## 제한과 확인 범위

입력 32MiB, 변환 엔진 기준 1~400페이지, 결과 64MiB, 실행 90초 제한이다. 브라우저 메모리와
장치 성능에 따라 이보다 작은 문서도 실패할 수 있다. 페이지 수는 파싱 이후 알 수 있으므로
대형 압축 문서의 초기 파싱 비용을 완전히 제한하는 장치는 아니다. 페이지 검사로 한 번,
PDF 출력으로 한 번 파싱한다. 속도 수치는 이 두 단계를 포함한다.

ECR 서버의 기존 PDF 8MiB 제한은 유지한다. 변환된 PDF가 크면 분석 요청을 보내지 않고 안내한다.
변환 화면에서는 64MiB 이하 PDF를 다운로드할 수 있으므로 별도로 나눠 분석할 수 있다.
일반 HWP 5·HWPX를 대상으로 하며 암호/배포용/손상 문서 및 일부 도형·수식·복잡한 조판은
지원하지 않을 수 있다. 대체 글꼴 때문에 줄바꿈·쪽 배치가 원본과 달라질 수 있다.
PDF의 한글 텍스트와 표를 확인했지만 한컴 출력과의 완전 일치를 보장하지 않는다.
특히 이 엔진 출력에서 PDFium 텍스트 추출이 영문·숫자를 일부 누락하는 사례가 있었다.
pypdf에서는 해당 문자열을 읽을 수 있어 로컬 단일 페이지 대조는 pypdf를 사용한다.
Cloudflare `AI.toMarkdown`의 실제 변환 품질은 이번 검사에서 원격 호출하지 않았으므로 미검증이다.
이미지 분석에는 렌더링한 페이지를 사용하고, 모델의 규격 분류·누락은 별도로 확인해야 한다.

2026-10-05, 이 PC의 Edge headless, 로컬 정적 서버에서 관찰한 결과:

| 표본 | 엔진 페이지 | PDF | Worker 처리 시간 |
| --- | ---: | ---: | ---: |
| 철도공사 AI 인프라 규격 HWP | 3 | 0.12MiB | 0.6초 |
| 상수도 디지털 ARS HWPX | 174 | 8.82MiB | 7.7초 |
| 빅데이터 활용체계 HWPX 확장자, 실제 HWP 5 | 274 | 15.41MiB | 12.4초 |

시그니처로 읽으므로 세 번째 파일처럼 확장자가 잘못 붙은 문서도 변환됐다.
3개 출력 모두 한글 텍스트 추출이 가능했다. 앞의 두 문서에서 진단 정규식으로 검출한
ECR 번호 집합은 원본과 같았고, 세 번째 문서는 같은 정규식에 해당하는 번호가 없었다.
**번호 보존은 모든 규격·표·그림 보존의 증거가 아니다.** 표본 전체를 육안 대조한 결과도 아니다.
기기 성능·네트워크·문서 구조에 따라 변환 시간은 달라진다.

첫 번째 변환 PDF의 1쪽을 로컬 `qwen3.5:4b` 이미지 분석에 넣어 ECR-001 GPU 서버 항목이
반환되는 것도 확인했다(`test-results/hwp-vision/`). CPU·메모리 문자열을 PDF 텍스트와
대조할 수 있었지만 수량 누락·NIC 문구 오독·캐시 항목 오분류가 남았다. 이는 변환에서
로컬 모델까지의 연결 검사이며 규격 추출 정확도 통과로 간주하지 않는다.

추가 KOTRIS 실문서 시험에서는 307페이지 / 12.74MiB PDF를 55.8초에 생성했다.
이 문서를 수용하도록 페이지 제한을 300에서 400으로 조정했다. **변환 품질은 실패다.**
PDF 188쪽(인쇄 186쪽)의 ECR-006 중첩 표가 부모 셀 경계에서 잘려 아래 장비 행이 보이지 않는다.
pypdf 텍스트에는 해당 행과 요구사항 번호가 남으므로 텍스트·번호 보존만으로 이 오류를 잡을 수 없다.
해당 페이지의 실제 Ollama 분석도 보이는 서버 2종만 반환했다. PDF 19쪽의 HW 개요 표는
전체 행이 보이지만 다른 위치의 표이며 수량 차이도 있어 ECR-006의 대체 근거로 자동 병합하지 않는다.
원본·캡처·결과는 `test-results/kotris/`에 있다. 엔진의 중첩 표 조판 문제는 해결되지 않았다.

원본·PDF·캡처·수치 보고서는 Git 제외 경로 `samples/`, `test-results/hwp-browser/`에만 있다.
표본을 바꿔 실제 브라우저 검사와 텍스트 진단을 다시 실행할 수 있다:

```powershell
node tools/browser-convert.cjs "samples/example.hwp" "samples/example.hwpx"
python -X utf8 -B tools/check-converted-pdf.py test-results/hwp-browser/summary.json --deps test-results/ecr-python
```

첫 도구는 실제 PDF 다운로드, 화면 응답, 취소, 잘못된 입력, 모바일 너비, 외부 통신·업로드 없음을
확인한다. 두 번째 도구는 pypdf·pypdfium2·olefile이 필요하며 원본과 PDF의 번호 집합을 비교하고
대표 페이지를 렌더링한다. 모든 추출 규격의 정답 판정이나 원본 조판 비교를 대신하지 않는다.

`npm test`는 단위·자산 해시·ECR 변환 연결 검사, `npm run test:browser`는 일반 공고 화면의
데스크톱·모바일 연결 검사다. 실제 RFP는 저장소에 포함하지 않으므로 위 실문서 검사는 별도 실행한다.
