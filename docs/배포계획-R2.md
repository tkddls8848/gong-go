# dev 브랜치 배포 계획 — R2 방식

[배포계획.md](배포계획.md) 9장 "대안 — R2로 전환하는 기준"을 실행 계획으로 편 문서다.
0단계(데이터 규모 재측정)를 마친 결과를 근거로 **R2 방식을 택한다.** Git-정적 방식과 겹치는
단계는 원문을 가리키고, 달라지는 부분만 여기서 다시 쓴다.

---

## 1. 실측 결과 (2026-08-03, 로컬 `dev` = `70da9e8`)

```powershell
du -sh data/pre data/bid data/raw
find data/pre data/bid -name "*.csv.gz" | wc -l
```

| 항목 | 실측 | 배포계획.md 2장 추정 |
|---|---|---|
| 배포 대상 gzip (`pre`+`bid`) | **288.3 MB** (pre 58 MB, bid 242 MB) | 약 190 MB |
| 파일 수 | **4,754개** + `index.json` 560 KB | 약 1,150개 |
| 최대 파일 | 335 KB (`bid/2023/12/11.csv.gz`) | 1 MB 미만 |
| 수집 범위 | 2020-01-01 ~ 2026-08-02, 3,213,444건 | 2025-01-01 ~ (575일) |
| `data/raw` (170컬럼 원본) | **651 MB** — 커밋 금지 | 계획서에 없던 항목 |
| `data/analysis` | 없음 (analyzer 미실행) | — |

추정이 빗나간 이유는 `sync.config.json`의 `begin`이 `2025-01-01`이 아니라 **`2020-01-01`**이기
때문이다. 기간이 4.5배라 파일 수도 4배가 됐다. 반대로 총량이 추정의 1.5배에 그친 것은
서비스 컬럼 슬림화(29컬럼) 덕이다 — 170컬럼 원본은 `data/raw`에 651 MB로 따로 남아 있다.

### 2장 기준선과의 대조

**288 MB는 2장이 정한 500 MB 선 아래다.** 즉 총량만 보면 Git-정적도 아직 성립한다.
그럼에도 R2를 택하는 근거는 총량이 아니라 아래 다섯 가지다.

| # | 근거 | 내용 |
|---|---|---|
| 1 | **되돌릴 수 없다** | Git에 288 MB를 한 번 커밋하면 빼내는 데 히스토리 재작성(`filter-repo` + force push)이 필요하고 기존 클론이 전부 깨진다. R2는 버킷을 지우면 끝난다. 비대칭이 큰 결정은 되돌릴 수 있는 쪽으로 간다 |
| 2 | **500 MB 선이 가깝다** | 2025년이 결손 상태다(696파일·328,727건 — 2024년 724파일·560,341건 대비). 백필하면 +약 15 MB. 여기에 `collector.js`의 기본 `begin`은 `2015-01-01`이라 범위를 조금만 넓혀도 선을 넘는다 |
| 3 | **히스토리는 영구 누적된다** | 크론이 최근 35일을 재수집하며 gzip을 덮어쓴다. 변경분은 델타 압축이 안 되는 바이너리라 통째로 히스토리에 쌓인다. 보수적으로 하루 6~10개 파일 변경 × 41 KB ≈ 연 90~150 MB, 재수집 창이 전부 바뀌는 최악에는 연 1 GB. 초기 288 MB에 얹히면 GitHub 권고선 1 GB까지 1~4년 |
| 4 | **파일 수 여유가 생각보다 없다** | 4,754개는 Pages 20,000 한도의 24%다. 연 1,460개씩 늘고, 여기에 `analysis/bid/<공고번호>.json`이 공고 1건당 1개로 붙는다. 지금은 관심 기관 2곳(`download.config.json`)뿐이라 수백 개지만 대상을 넓히면 한도가 실질 제약이 된다 |
| 5 | **`data/raw` 651 MB를 살릴 수 있다** | Git에는 영원히 못 넣는다(`.gitignore`에 명시). R2에는 같은 버킷의 `raw/` 프리픽스로 두고 라우팅 정규식에서 차단하면 된다. 288+651=939 MB로 무료 10 GB 안이다 |

**한 가지 확인된 유리한 사실.** `zlib.gzipSync`는 MTIME 필드를 0으로 쓰므로 같은 입력에
항상 같은 바이트를 낸다(실측 확인). 재수집해도 내용이 같으면 파일이 바뀌지 않는다.
Git-정적이었다면 헛커밋을 막아 줬을 성질이고, R2에서는 해시 비교로 헛업로드를 막아 준다.
**다만 이것은 쓰기(Class A)에만 해당한다.** 읽기 과금은 조회 횟수가 정하며 병목도 그쪽이다 — 5장.

**R2의 대가는 5장에 적는다** — `/data`가 무료·무제한 정적 자산에서 과금 대상 Functions
호출로 바뀐다. 이 점이 이 계획의 유일한 실질 리스크다.

## 2. Git-정적 계획과 달라지는 것

| 배포계획.md 단계 | R2 방식 |
|---|---|
| 5-1 `.gitignore` 축소 | **불필요.** `data/`를 통째로 제외한 현재 상태를 그대로 둔다 |
| 5-2 `build.sh` 작성 | **불필요.** 빌드 명령 없이 출력 디렉터리 `public`만 지정한다 |
| 5-3 `DATA_BASE` → `/data` | **그대로 필요** (R2-3) |
| 5-4 게이트 이식 | **그대로 필요** (R2-4) |
| 5-5 `SYNC_BEGIN`/`SYNC_END` | **그대로 필요** (R2-5) |
| 6장 크론 "커밋·푸시" | **업로드로 교체.** `uploader/upload.js`로 R2에 PUT (R2-7) |
| — | **신규:** R2 버킷·바인딩 (R2-1), 중계 Function (R2-2), 월별 봉인 (R2-6), 업로더 (R2-7) |

부수 효과 두 가지가 따라온다.

- **크론이 Pages 재배포를 트리거하지 않는다.** 데이터가 저장소에 들어가지 않으므로 푸시가
  없다. 빌드 500회/월 한도와 무관해지고, 수집 직후 빌드 대기 없이 바로 반영된다.
  Pages 배포는 코드를 고칠 때만 일어난다.
- **로컬 실행법이 안 바뀐다.** `DATA_BASE`를 절대경로 `/data`로 바꿔도 `devserver/server.js`가
  저장소 루트를 서빙하므로 로컬에서는 그대로 `data/`를 읽는다. 배포본에서는 같은 경로가
  Function으로 잡힌다. 5-3이 걱정한 "로컬 실행법이 바뀐다"는 R2 방식에서는 발생하지 않는다.

## 4. 단계별 실행

### R2-1. 버킷과 바인딩

1. R2 버킷 `gong-go-data` 생성. **공개 접근(Public bucket)은 비활성화.** 접근은 전부
   Pages Function을 통해서만 이뤄진다.
2. Pages 프로젝트 → Settings → Functions → R2 bucket bindings → 변수명 **`DATA`** → 버킷
   `gong-go-data`. **Production과 Preview 양쪽에 건다** (한쪽만 걸면 그쪽에서 `env.DATA`가
   `undefined`가 되어 500이 난다).
3. R2 API 토큰 발급(Object Read & Write, 버킷 한정). 업로더용 자격증명 3종을 얻는다:
   `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`.

**검증:** 대시보드에서 버킷이 비어 있고 Public URL이 꺼져 있는지 확인.

### R2-2. 중계 Function — `functions/data/[[path]].js`

배포계획.md 9장의 예시 코드를 세 군데 고쳐서 쓴다.

```js
// R2 버킷을 게이트 뒤에서 중계한다. 허용 키 외에는 전부 404.
// Content-Encoding은 절대 붙이지 않는다 — 프런트가 DecompressionStream으로 직접 해제하므로
// 여기서 붙이면 브라우저가 먼저 풀어 이중 처리로 깨진다(배포계획.md 5-2와 같은 제약).
// (pre|bid)/YYYY/MM/DD.csv.gz (일별) 과 (pre|bid)/YYYY/MM.csv.gz (월별 봉인, R2-6) 을 함께 받는다.
const KEY = /^(index\.json|analysis-index\.json|(pre|bid)\/\d{4}\/\d{2}(\/\d{2})?\.csv\.gz|analysis\/bid\/[^/]{1,160}\.json)$/;
const RECENT_DAYS = 40;   // 크론 재수집 창(35일)보다 넉넉히

export async function onRequestGet({ request, env, params }) {
  const key = (Array.isArray(params.path) ? params.path : [params.path]).join("/");
  if (!KEY.test(key)) return new Response("Not found", { status: 404 });

  const object = await env.DATA.get(key, { onlyIf: request.headers });
  if (!object) return new Response("Not found", { status: 404 });

  const headers = new Headers({
    "Content-Type": key.endsWith(".json") ? "application/json; charset=utf-8" : "application/gzip",
    "Cache-Control": cacheControl(key),
    "ETag": object.httpEtag,
  });
  // onlyIf 조건이 맞으면 본문 없는 R2Object가 온다 = 클라이언트 캐시가 최신.
  if (!object.body) return new Response(null, { status: 304, headers });
  return new Response(object.body, { headers });
}

// 과거 날짜 파일은 불변이므로 오래 캐시하고, 재수집 창 안쪽만 짧게 잡는다.
// public이 아니라 private인 이유는 게이트 뒤 응답을 공유 캐시에 남기지 않기 위해서다.
function cacheControl(key) {
  if (key.endsWith("index.json")) return "private, max-age=60";
  // 월별 봉인 파일은 재수집 창 밖에서만 만들어지므로(R2-6) 언제나 불변이다.
  if (/^(pre|bid)\/\d{4}\/\d{2}\.csv\.gz$/.test(key)) return "private, max-age=31536000, immutable";
  const date = key.match(/(\d{4})\/(\d{2})\/(\d{2})\.csv\.gz$/);
  if (!date) return "private, max-age=3600";
  const days = (Date.now() - Date.parse(`${date[1]}-${date[2]}-${date[3]}T00:00:00Z`)) / 86400000;
  return days > RECENT_DAYS ? "private, max-age=31536000, immutable" : "private, max-age=300";
}
```

원문 9장 코드에서 바꾼 세 가지:

| 바꾼 것 | 이유 |
|---|---|
| `analysis/bid/[\w-]+\.json` → `[^/]{1,160}` | `analyzer/analyze.js:198`의 `safeNotice`는 `<>:"/\|?*`와 제어문자만 걸러낸다. 공고번호에 점·공백·한글이 들어가면 `[\w-]+`가 404를 낸다. R2 키는 평면 문자열이라 `/`만 막으면 경로 탈출은 성립하지 않는다 |
| `public,` → `private,` | 게이트 뒤 응답이다. `public`이면 공유 캐시에 남아 게이트를 우회할 여지가 생긴다 |
| 고정 `max-age=86400` → 날짜별 분기 | 과거 날짜는 불변이라 1년 캐시가 맞고, 재수집 창 안쪽은 매일 바뀌므로 5분이 맞다. 5장의 호출량 문제를 줄이는 주된 수단이다 |

**검증:** 배포 후 `curl -I` 두 번.
- `/data/bid/2023/12/11.csv.gz` → `200`, `Content-Type: application/gzip`,
  **`Content-Encoding` 헤더 없음**, `Cache-Control: private, max-age=31536000, immutable`
- `/data/raw/bid/2023/12/11.csv.gz`, `/data/state/sync-state.json` → 둘 다 `404`

### R2-3. 프론트 경로와 `dataToken` 제거

`public/app.js:1`의 `DATA_BASE`를 `"../data"` → `"/data"`로 바꾼다.
`public/app.js:22`의 `file:` 안내 문구는 로컬 실행법이 유지되므로 그대로 둬도 되지만,
배포본에서 뜰 문구는 아니므로 다듬는다.

**그리고 `dataToken`을 없앤다. 이게 이 단계에서 가장 중요하다.**

```js
// app.js:29 — 수집기가 돌 때마다 값이 바뀌고, app.js:101에서 모든 파일 URL에 공통으로 붙는다.
dataToken = index.updatedAt ? `?v=${Date.parse(index.updatedAt) || 0}` : "";
```

쿼리스트링은 브라우저 캐시 키의 일부다. 따라서 **매일 수집이 끝날 때마다 4,754개 URL이
전부 새 URL이 되어 캐시가 통째로 무효화된다.** R2-2에서 과거 날짜에 `immutable`을 걸어도
이 토큰이 있는 한 아무 효과가 없고, 5장의 호출량 완화책 1번이 성립하지 않는다.

| | 전 구간 조회 1회당 Function 호출 |
|---|---|
| 토큰 유지 | **4,754회** — 매일, 사용자마다 반복 |
| 토큰 제거 | 최초 1회만 4,754회, 이후 재수집 창 40일치 **약 80회** |

토큰의 원래 역할(정적 서빙에서 과거 파일이 굳는 것 방지)은 R2-2의 중계 Function이
날짜별 `Cache-Control` 분기와 `ETag`로 이미 수행한다. 중복이므로 제거한다.
`index.json`에 붙는 `?t=${Date.now()}`(`app.js:28`)는 남긴다 — 목록 자체는 항상 최신이어야
하고, 파일 1개라 호출량에 영향이 없다.

**그리고 파일 선택을 범위 인지로 바꾼다.** R2-6의 월별 봉인이 들어오면 인덱스 항목 하나가
하루가 아니라 한 달을 덮는다.

```js
// app.js:90 — 현재: 항목 하나 = 하루
const files = fileIndex.filter((file) => file.date >= begin && file.date <= end);

// 바꾼 뒤: 항목의 구간과 조회 구간이 겹치면 받는다
const files = fileIndex.filter((file) => file.end >= begin && file.begin <= end);
```

인덱스 항목 스키마를 `{mode, date, path, count}` → **`{mode, begin, end, path, count}`**로 통일한다
(일별 항목은 `begin === end`). `collector.js`의 인덱스 생성부와 `compact.js`가 같은 형태를 쓴다.

월을 통째로 받아도 **결과는 정확하다.** `app.js:92`의 행 단위 필터가 이미
`date >= from && date <= to`로 걸러내기 때문이다. 오버페치는 정확성이 아니라 전송량 문제이고,
재수집 창 안쪽을 일별로 남겨 두는 이유가 그것이다(R2-6).

**검증 1:** 로컬 `npm run serve` → `http://localhost:8788/public/` 에서 목록이 그대로 나온다
(devserver가 루트를 서빙하므로 `/data`가 그대로 맞는다). 여기서 깨지면 배포본도 깨진다.

**검증 2 (배포 후):** 개발자도구 Network에서 전 구간 조회를 두 번 한다. 두 번째 조회의
과거 날짜 파일이 `(disk cache)` 또는 `304`로 잡히고 네트워크 요청 수가 4,754 → 100 미만으로
떨어지는지 확인한다. 안 떨어지면 캐시를 깨는 다른 요인이 남아 있는 것이다.

### R2-4. 게이트 이식

배포계획.md 5-4와 동일. `main`의 `functions/_middleware.js`를 `dev`의 같은 경로로 수정 없이
복사한다. `GATE_PASSWORD`가 비면 통과 모드라는 점도 동일하므로 **7장 순서를 지킨다.**

**검증:** 시크릿 창으로 접속해 로그인 화면이 뜨는지, `/data/index.json`을 직접 열어도
막히는지 확인.

```js
const begin = parseDate(process.env.SYNC_BEGIN || config.begin || "2015-01-01");

```

### R2-6. 월별 봉인 — `collector/compact.js`

호출당 비용을 줄이는 두 번째 수단이다. R2-3의 `dataToken` 제거가 **재방문**을 잡는다면,
봉인은 **최초 방문과 `index.json`**을 잡는다. 성격이 달라 둘 다 한다.

**압축률이 목적이 아니다.** 한 달치를 이어붙여 재압축해도 용량은 0.7%밖에 안 준다(실측:
bid 2023-12 4,545 KB → 4,525 KB). DEFLATE의 사전 창이 32 KB뿐이라 파일을 붙여도 압축기가
멀리 있는 반복을 보지 못한다. 얻는 것은 **파일 수 = 호출 수**다.

#### 연령별 2단 레이아웃

| 구간 | 저장 | 키 | 파일 수 |
|---|---|---|---|
| 최근 40일 (재수집 창) | 일별 유지 | `{pre,bid}/YYYY/MM/DD.csv.gz` | 80 |
| 그 이전 완료 월 | 월별 봉인 | `{pre,bid}/YYYY/MM.csv.gz` | 156 |
| | | | **236** |

재수집 창 안쪽은 매일 바뀌므로 묶지 않는다. 묶으면 당월 4.5 MB가 매일 캐시에서 날아가
82 KB를 받던 사용자가 4.5 MB를 받게 되어 오히려 손해다. **창 밖으로 완전히 나간 월만** 봉인한다.

효과:

| 조회 | 현재 | 봉인 후 |
|---|---|---|
| 최근 7일 | 14 | **14** (변화 없음) |
| 최근 3개월 | 182 | **86** |
| 2024년 한 해 | 732 | **24** |
| 전 구간 | 4,754 | **236** |
| `index.json` 크기 | 560 KB | **약 30 KB** |

`index.json`은 `?t=`가 붙어 페이지를 열 때마다 새로 받는다. 조회를 안 해도 나가는 비용이라
560 KB → 30 KB가 체감상 가장 크다.

#### 동작

```
node collector/compact.js [--dry-run] [--prune]
```

1. **대상 선정.** 월의 마지막 날 + `SEAL_LAG`(40일) < 오늘 인 월만 고른다. 이미 봉인된 월
   (`YYYY/MM.csv.gz`가 있고 그 월의 일별 파일이 없음)은 건너뛴다.
2. **헤더 검증.** 그 월 일별 파일들의 헤더가 전부 같은지 먼저 본다. **다르면 그 월을 건너뛰고
   경고한다.** 현재는 전 구간이 29컬럼으로 통일돼 있지만(실측), 컬럼이 바뀐 시기가 섞여 있으면
   조용히 어긋난 CSV를 만드는 것이 최악이다.
3. **병합.** 날짜 오름차순으로, BOM 1회 + 헤더 1회 + 각 파일의 본문을 이어붙여 gzip으로 쓴다.
4. **행 수 대조.** 봉인 전 일별 합계와 봉인 후 행 수가 같아야 한다. 다르면 중단하고 아무것도
   지우지 않는다.
5. **인덱스 갱신.** 그 월의 일별 항목들을 `{mode, begin: "YYYY-MM-01", end: "YYYY-MM-말일",
   path: "bid/YYYY/MM.csv.gz", count: 합계}` 하나로 교체한다.
6. **원본 정리는 별도 플래그.** 기본은 일별 파일을 남긴다. `--prune`을 줬을 때만 지운다.
   봉인 결과를 확인한 뒤 지우는 2단계가 안전하고, `data/raw/`에 170컬럼 원본이 일별로
   남아 있어 최후 복구 경로도 있다.

**멱등하다.** 이미 봉인된 월은 대상이 아니고, `zlib.gzipSync`가 결정적이라(1장) 다시 돌려도
같은 바이트가 나와 업로더가 재업로드하지 않는다. 크론에서 매일 돌려도 대상이 없으면 0건이다.

**로컬 경로 충돌 없음.** `data/bid/2023/12.csv.gz`(파일)와 `data/bid/2023/12/`(디렉터리)는
이름이 달라 공존한다. R2는 평면 키라 애초에 문제가 없다.

**검증:**
- `node collector/compact.js --dry-run` → 대상 월 수와 봉인 전후 파일 수(4,754 → 236) 출력
- 실행 후 `index.json`의 `count` 총합이 **3,213,444로 유지**되는지 확인. 여기가 틀리면 병합이 깨진 것이다
- 로컬 `npm run serve`에서 2023년 조회 결과가 봉인 전과 같은 건수인지 대조
- 한 번 더 실행 → **0건** (멱등성)

### R2-7. 업로더 — `uploader/upload.js`

R2의 S3 호환 엔드포인트(`https://<ACCOUNT_ID>.r2.cloudflarestorage.com`, region `auto`)에
PUT한다. **`@aws-sdk/client-s3`를 의존성으로 추가한다.** 현재 저장소는 의존성이 0개고
`package-lock.json`도 없으므로 이 결정에는 대가가 있다.

| 선택지 | 판단 |
|---|---|
| `@aws-sdk/client-s3` | **채택.** 페이지네이션·재시도·서명이 검증돼 있다. 의존성 1개와 lock 파일이 생긴다 |
| `node:crypto`로 SigV4 직접 서명 | 의존성 0을 지키지만 서명·XML 파싱을 직접 짜야 한다. 4,754개 초기 적재에서 틀리면 디버깅이 비싸다 |
| `wrangler r2 object put` | 부적합. 파일당 프로세스 기동이라 초기 적재에 몇 시간이 걸린다 |

동작:

1. `ListObjectsV2`로 버킷의 키+ETag를 전부 받는다(1,000개씩 5회). R2의 ETag는 단일 PUT
   객체에서 MD5와 같다.
2. 로컬 `data/{pre,bid}/**/*.csv.gz`(일별·월별 모두), `index.json`, `analysis-index.json`,
   `analysis/bid/*.json`의 MD5를 계산해 ETag와 다른 것만 고른다. **별도 상태 파일이 필요 없다**
   — 러너가 매번 새 체크아웃에서 시작해도 버킷 자체가 상태다.
3. `shared/pipeline-utils.js`의 `mapPool`로 동시성 8로 PUT.
   `ContentType`은 `.csv.gz` → `application/gzip`, `.json` → `application/json; charset=utf-8`.
   **`ContentEncoding`은 설정하지 않는다.**
4. **업로드·삭제 순서를 지킨다.** R2는 트랜잭션이 없으므로 순서가 유일한 방어다.

   ```
   ① *.csv.gz (일별·월별) PUT
   ② index.json PUT
   ③ 봉인으로 대체된 일별 키 DELETE      ← 인덱스가 바뀐 뒤에 지운다
   ④ analysis-index.json PUT
   ```

   ①보다 ②가 먼저면 아직 없는 파일을 프런트가 요청한다. ②보다 ③이 먼저면 구 인덱스를
   캐시한 브라우저가 사라진 일별 파일에서 404를 만난다.
5. **봉인으로 남겨진 일별 키를 지운다.** R2-6이 로컬에서 월별로 묶어도, R2에 이미 올라간
   일별 객체는 저절로 사라지지 않는다. 삭제 조건은 다음 하나뿐이다.

   > `(pre|bid)/YYYY/MM/DD.csv.gz` 를 지운다 — **버킷에 `(pre|bid)/YYYY/MM.csv.gz` 가 있을 때만.**

   **"로컬에 없으면 지운다"로 만들면 안 된다.** 크론 러너는 최근 35일치만 수집한 상태이므로
   그 규칙이면 나머지 전부가 삭제 대상이 된다. 위 조건은 버킷 안의 정보만으로 판정되므로
   로컬이 부분적이어도 안전하다. `state/`·`raw/`·`analysis/` 프리픽스는 애초에 대상이 아니다.
6. `sync-state.json`은 `state/` 프리픽스로 왕복한다(뷰어 라우팅에서 차단되는 위치).
7. `--dry-run`으로 대상 건수·총 바이트·삭제 예정 키 수를 출력하는 경로를 둔다.

**검증:** 로컬에서 `node uploader/upload.js --dry-run` → 4,755건. 실행 후 한 번 더 →
**0건**(ETag 비교가 동작한다는 뜻). 대시보드에서 버킷 크기가 288 MB 근처인지 확인.

### R2-8. 크론 — `.github/workflows/collect.yml`

배포계획.md 6장의 브랜치 제약이 그대로 적용된다: **워크플로 파일은 `main`에 두고**
잡에서 `ref: dev`를 체크아웃한다(`on: schedule`은 기본 브랜치의 워크플로만 트리거한다).
달라지는 건 마지막 단계뿐이다 — 커밋·푸시 대신 업로드.

```yaml
on:
  schedule:
    - cron: "0 20 * * *"   # UTC 20:00 = KST 05:00
  workflow_dispatch:
    inputs:
      begin: { description: "수집 시작일(YYYY-MM-DD). 비우면 최근 35일.", default: "" }
      end:   { description: "수집 종료일(YYYY-MM-DD). 비우면 오늘.",      default: "" }
```

- `actions/checkout@v4` (`ref: dev`) → Node 20 → `npm ci`
- R2에서 `state/sync-state.json` 내려받기 → `node collector/collector.js` → `node uploader/upload.js`
- **범위:** `SYNC_BEGIN`으로 최근 35일. 과거 날짜는 R2에 이미 있는 객체를 승계한다
- **실패 처리:** `data/sync-errors.json`이 비어 있지 않으면 워크플로 실패
- **Secret 4개:** `SERVICE_KEY`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`
- **쓰기 권한 불필요:** 저장소에 푸시하지 않으므로 `permissions: contents: read`로 족하다.
  Git-정적 방식보다 권한이 좁아지는 이점이 있다

**`compact.js`는 크론에 넣지 않는다.** 러너는 최근 35일치만 로컬에 갖고 있어서 과거 월을
묶을 재료가 없다. 봉인은 **전체 데이터가 있는 로컬에서 월 1회** 돌린다 — 이미 downloader·
converter·analyzer를 로컬에서 수동 실행하는 것과 같은 자리다.

```powershell
node collector/compact.js --dry-run   # 대상 확인
node collector/compact.js             # 봉인
node uploader/upload.js               # 월 파일 업로드 + 대체된 일별 키 삭제
node collector/compact.js --prune     # 검증 후 로컬 일별 파일 정리
```

러너가 하루 늦게 도는 사이 봉인이 반영돼도 문제없다. 업로더의 삭제 조건이 버킷 상태만
보기 때문이다(R2-7 5번).

**검증:** `workflow_dispatch`로 1회 수동 실행 → R2 객체 수가 늘고, 재배포 없이 브라우저
새로고침만으로 새 날짜가 보이는지 확인.

## 5. 비용과 한도 — Functions 호출이 유일한 압박점

| 항목 | 무료 한도 | 실측 대비 |
|---|---|---|
| R2 저장 | 10 GB | 288 MB (`raw/` 포함해도 939 MB) — 여유 |
| R2 이그레스 | 무료 | — |
| R2 Class A (쓰기) | 100만/월 | 초기 4,755회 + 일 10~70회 — 여유 |
| R2 Class B (읽기) | 1,000만/월 | 조회량에 비례 — 여유 |
| Pages 빌드 | 500회/월 | 코드 변경 시에만 — 대폭 여유 |
| **Pages Functions 요청** | **10만/일 (무료 플랜)** | **전 구간 조회 1회 = 236 요청** (대책 전 4,754) |

마지막 줄이 R2 방식의 대가다. Git-정적에서는 `/data/**`가 무료·무제한 정적 자산이지만,
R2에서는 파일 하나가 Function 호출 하나다. `public/app.js:1`의 `LOAD_CONCURRENCY = 12`로
전 구간을 조회하면 대책 없이는 한 번에 4,754회가 나가고, 하루 21회면 무료 한도를 소진한다.

**R2-3(`dataToken` 제거)과 R2-6(월별 봉인)을 적용하면 이 문제는 사실상 사라진다.**

| | 대책 전 | R2-3 + R2-6 |
|---|---|---|
| 전 구간 조회 (캐시 없음) | 4,754 | **236** |
| 전 구간 조회 (재방문) | 4,754 | **약 80** |
| 최근 7일 조회 | 14 | **14** |
| 5명 × 일 10회 조회 | 최대 237,700/일 (한도 초과) | **약 2,000/일 (한도의 2%)** |

**계정 단위 공유에 주의한다.** Workers 무료 한도는 프로젝트가 아니라 **계정 전체**에
적용된다. `main`의 `gong-go` 앱도 `functions/api/[[path]].js`로 나라장터 API를 실시간
프록시하므로 같은 quota를 쓴다. 7장 1번에서 기존 사용량을 먼저 확인한다 — 남은 여유가
10만이 아닐 수 있다.

### 쓰기와 읽기를 섞지 않는다

| | 발생 원인 | 규모 | 병목인가 |
|---|---|---|---|
| Class A (쓰기) | 업로더 PUT·LIST | 초기 4,755회 + 일 10~70회 | 아니다 (월 100만) |
| Class B (읽기) | 브라우저 조회 | 조회량 비례 | 아니다 (월 1,000만) |
| **Functions 호출** | **브라우저 조회** | **조회량 비례** | **여기가 먼저 걸린다** |

`zlib.gzipSync`의 결정성(1장)이 아껴 주는 것은 **Class A뿐이다.** 내용이 같으면 ETag가 같아
업로드를 건너뛴다. 하지만 Class A는 애초에 병목이 아니므로 이 절약은 여유 위에 여유를 더한다.
**읽기 과금은 결정성과 무관하게 사용자 조회 횟수가 정한다.**

결정성이 읽기에 간접 기여하는 부분은 있다. ETag가 안정적이라 `304`와 브라우저 캐시가
설계대로 동작한다 — 결정적이지 않았다면 재수집 창 35일치가 내용이 같아도 매일 ETag가
바뀌어 다시 내려받았을 것이다. 다만 **`304` 응답도 Function 호출 1회와 Class B 1회로
계산된다**(대시보드에서 확인할 것). 요청 수를 실제로 없애는 것은 브라우저 캐시가 유효해
요청이 아예 나가지 않는 경우뿐이다. 그래서 R2-3의 `dataToken` 제거가 결정적이다.

### 완화 수단 (싼 것부터)

1. **`dataToken` 제거 (R2-3)** — 한 줄이다. 이것이 선행 조건으로, 토큰이 남아 있으면 2번의
   캐시 분기가 매일 무효화되어 효과가 0이 된다. **재방문**을 잡는다
2. **R2-2의 날짜별 캐시 분기** — 과거 날짜는 `immutable` 1년이라 같은 사용자의 반복 조회가
   두 번째부터 요청을 내지 않는다. 1번과 짝이 되어야 동작한다
3. **월별 봉인 (R2-6)** — 파일 수를 4,754 → 236으로 줄인다. 1·2번이 못 잡는
   **최초 방문과 `index.json`(560 KB → 30 KB)**을 잡는다. 1번과 성격이 달라 둘 다 한다
4. **조회 범위 상한** — 배포계획.md 10장의 "최대 31일" 제한. 1~3번으로 한도의 2%면
   UX를 깎을 이유가 없으므로 보류한다
5. **`Workers Paid` $5/월** — 1,000만 요청/월 포함. 위로 부족해지면 그때 켠다

검토했다가 접은 안: **`/data/range?begin=&end=` 로 한 번에 받아 Function 안에서 R2를
여러 번 읽어 합치기.** Functions 호출은 1회가 되고 R2 Class B로 N회가 옮겨가, 무료 한도가
3배 넉넉한 쪽으로 병목을 미는 효과가 있다. 다만 Workers 무료 플랜의 **호출당 서브리퀘스트
제한(50)**에 걸리고(R2 바인딩 호출이 여기 포함되는지는 확인 필요), 여러 gzip 스트림을
이어 붙이면 프런트의 `DecompressionStream` 처리가 복잡해진다. 1~3번으로 한도의 2%라
이 복잡도를 살 이유가 없다.

무료 한도 수치는 플랜에 따라 바뀌므로 **7장 1번에서 대시보드로 확인하고 진행한다.**
확인 없이 단정하지 않는다.

## 6. 보안

배포계획.md 8장을 그대로 승계하고 R2 관련 항목만 더한다.

| 항목 | 상태 |
|---|---|
| 버킷 공개 접근 | 비활성화. Public URL을 켜면 게이트가 통째로 무의미해진다 — 켜지 않는다 |
| 라우팅 화이트리스트 | `KEY` 정규식에 맞는 키만 중계. `raw/`·`state/`는 구조적으로 도달 불가 |
| 게이트 뒤 캐시 | `private`로만 응답. 공유 캐시에 데이터가 남지 않는다 |
| R2 자격증명 | Actions Secret으로만 주입. 버킷 한정 토큰, 클라이언트 노출 없음 |
| `data/raw` 170컬럼 원본 | R2 `raw/` 프리픽스에 두더라도 뷰어 경로로는 도달 불가 |
| 저장소 쓰기 권한 | 크론이 푸시하지 않으므로 `contents: read`로 축소 |

게이트가 단일 공유 암호인 한계는 동일하다. 사용자가 늘면 Cloudflare Access(SSO)로 교체를
검토한다.

## 7. 대시보드·시크릿 작업

**순서를 지킨다.** 2번 전에 3번을 하면 데이터가 무방비로 공개된다.

1. Pages 새 프로젝트 `gong-go-archive` 생성 → 저장소 연결
   - 프로덕션 브랜치 `dev`, **빌드 명령 비움**, 출력 디렉터리 `public`, 프리뷰 브랜치 `None`
   - 이때 Functions 무료 한도(5장)를 대시보드에서 확인한다
2. 환경변수 `GATE_PASSWORD` — **Production과 Preview 양쪽 모두**
3. R2 바인딩 `DATA` — **Production과 Preview 양쪽 모두** (R2-1)
4. GitHub Secret 4개 등록 (R2-8)
5. 초기 봉인: 로컬에서 `node collector/compact.js` (4,754 → 236개, R2-6의 검증 항목 확인)
6. 초기 적재: `node uploader/upload.js` 1회 (288 MB·237건)
7. 배포 검증: 게이트 → 목록 → 첨부 모달 → ECR 탭 → CSV 다운로드 →
   R2-2의 `curl -I` 헤더 2종 → R2-3의 재조회 시 네트워크 요청 수 감소

`main`의 기존 `gong-go` 프로젝트는 프리뷰 브랜치가 `main`으로 제한돼 있어 `dev` 푸시의
영향을 받지 않는다.

## 8. 롤백

R2가 기대에 못 미치면(주로 5장의 Functions 호출량) Git-정적으로 되돌아갈 수 있다.
**데이터를 Git에 넣지 않았기 때문에 이 방향의 되돌리기가 싸다.**

1. `.gitignore` 축소 (배포계획.md 5-1)
2. `build.sh` 작성, Pages 빌드 명령 `bash build.sh` (5-2)
3. `functions/data/[[path]].js` 삭제 — 정적 `/data/**`가 그 자리를 대신한다
4. 크론의 업로드 단계를 커밋·푸시로 교체

`compact.js`(R2-6)는 롤백해도 그대로 쓴다. 오히려 Git-정적에서 더 유리하다 — 커밋 대상이
4,754개에서 236개로 줄어 클론·빌드 시간과 Pages 20,000 파일 한도 압박이 함께 내려간다.

`DATA_BASE = "/data"`, 게이트, `SYNC_BEGIN`은 양쪽 공통이라 그대로 남는다.
반대 방향(Git-정적 → R2)은 히스토리 재작성이 필요해 훨씬 비싸다 — 1장 근거 1의 내용이다.

| # | 작업 | 위치 | 배포계획.md 대응 |
|---|---|---|---|

| 4 | 게이트 복사 | `dev` | 5-4 |
| 5 | `SYNC_BEGIN`/`SYNC_END` | `dev` | 5-5 |
| 6 | **`collector/compact.js` 월별 봉인** | `dev` | R2-6 (신규) |
| 7 | `uploader/upload.js` + 의존성 | `dev` | R2-7 (신규) |
| 8 | Pages 프로젝트 + `GATE_PASSWORD` + `DATA` 바인딩 | 대시보드 | 7장 1~3 |

1~7까지 하면 로컬에서 배포 형태를 재현할 수 있다. 8~11까지 가면 자동 갱신이 붙는다.

호출당 비용을 줄이는 것이 3번과 6번이다. **3번은 한 줄, 6번은 새 스크립트 하나**이고
둘이 잡는 대상이 달라(재방문 / 최초 방문) 함께 넣어야 5장 표의 수치가 나온다.
