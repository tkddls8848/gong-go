# R2 배포·운영 가이드

`dev` 브랜치의 공고 CSV와 ECR 분석 결과는 비공개 Cloudflare R2 버킷에 저장하고,
Cloudflare Worker 하나가 인증 게이트를 먼저 실행한 뒤 정적 자산과 `/data/**` R2 중계를 처리한다.

이 문서는 2026-08-08 현재 저장소 구현을 기준으로 한다. Cloudflare·GitHub 대시보드의 외부 설정
상태는 저장소만으로 확인할 수 없으므로 체크리스트에서 별도 확인한다.

## 1. 현재 데이터 스냅샷

로컬 `data/index.json` 기준:

| 항목 | 값 |
|---|---:|
| 갱신 시각 | 2026-08-08 04:23:39 UTC |
| 데이터 범위 | 2020-01-01 ~ 2026-08-05 |
| 공고 수 | 3,219,569건 |
| 활성 인덱스 항목 | 285개 |
| 월별 봉인 | 154개 (pre 77, bid 77) |
| 최근 일별 파일 | 131개 (pre 66, bid 65) |
| 인덱스가 가리키는 gzip | 약 285.9 MiB |
| `index.json` | 약 41 KiB |
| `data/raw` 원본 백업 | 4,760개, 약 641.3 MiB |
| ECR 분석 결과 | 현재 로컬에 없음 |

`data/pre`와 `data/bid`의 디스크 사용량은 약 569.9 MiB다. 이는 봉인 후 아직 정리하지 않은
일별 파일이 월 파일과 공존하기 때문이며, 실제 서비스 목록은 `index.json`의 285개 항목만 사용한다.

서비스 CSV는 `shared/service-columns.js` 기준으로 본공고 30개, 사전공고 17개 컬럼을 보존한다.
전체 원본 컬럼은 `data/raw/`에 별도로 남으며 업로드 대상이 아니다.

## 2. 아키텍처

```text
[매일] GitHub Actions
  main의 schedule 트리거
    → dev 브랜치 체크아웃
    → npm ci
    → R2 state/sync-state.json 내려받기
    → 최근 35일 collector 실행 (--no-resume)
    → sync-errors.json 검사
    → uploader로 변경분 반영

[월 1회] 전체 로컬 데이터가 있는 운영 PC
  compact --dry-run → compact → 검증 → compact --prune → upload

Cloudflare Worker (wrangler.jsonc로 일괄 배포)
  src/worker.js                      공유 암호 인증 → 요청 라우팅
  public/                            Assets 바인딩의 정적 UI
  /data/**                           R2 바인딩 DATA 중계
              ↓
Cloudflare R2 (비공개)
  index.json
  pre|bid/YYYY/MM.csv.gz            완료 월
  pre|bid/YYYY/MM/DD.csv.gz         최근 재수집 창
  analysis-index.json
  analysis/bid/*.json
  state/sync-state.json             자동화 전용
```

Cloudflare 대시보드가 새 프로젝트 생성을 Workers 중심으로 유도하는 현재 흐름에서 Pages
`functions/` 규약은 Worker 프로젝트에 적용되지 않는다. 실제로 잘못 만든 Worker가 게이트 없이
정적 자산을 내보낸 사례가 있어 대시보드 설정에 의존하지 않는 단일 Workers 구조로 바꿨다.

`wrangler.jsonc`가 `public/` Assets와 `DATA` R2 바인딩을 선언한다. Workers Static Assets의
기본값은 asset-first이므로 `assets.run_worker_first: true`를 반드시 유지한다. 이 값이 있어야
`/`, `/app.js` 같은 실제 정적 파일도 `src/worker.js`의 게이트를 먼저 지난다. 근거는 Cloudflare
공식 [Static Assets configuration 문서](https://developers.cloudflare.com/workers/static-assets/binding/#run_worker_first)다.
로컬 조회 서버에서는 종전대로 `devserver/server.js`가 저장소 루트를 서빙하므로 동일한 `/data`
URL이 로컬 `data/`를 가리킨다.

## 3. 필요한 설정

### 로컬·GitHub Actions 환경변수

| 이름 | 필수 대상 | 설명 |
|---|---|---|
| `SERVICE_KEY` | collector | 공공데이터포털 일반 인증키(Decoding) |
| `R2_ACCOUNT_ID` | uploader | Cloudflare 계정 ID |
| `R2_ACCESS_KEY_ID` | uploader | 버킷 한정 API 토큰 Access Key |
| `R2_SECRET_ACCESS_KEY` | uploader | 버킷 한정 API 토큰 Secret Key |
| `R2_BUCKET` | 선택 | 기본값 `gong-go-data` |
| `SYNC_BEGIN`, `SYNC_END` | 자동화 시 | 이번 수집·삭제 판정 구간 |

로컬 값은 루트 `.env`에 둘 수 있다. `.env`는 Git에서 제외된다. GitHub에는 앞의 필수 4개를
Actions Secrets로 등록한다.

### Cloudflare Workers

| 종류 | 이름 | 값 |
|---|---|---|
| Secret | `GATE_PASSWORD` | 공유 접근 암호. `wrangler secret put`으로만 등록 |
| 환경변수 | `GATE_COOKIE_NAME` | 선택, 기본 `gong_gate` |
| R2 binding | `DATA` | `wrangler.jsonc`에 선언된 비공개 `gong-go-data` 버킷 |

Production에는 `GATE_PASSWORD` secret과 `DATA`가 모두 필요하다. `GATE_PASSWORD`를
`wrangler.jsonc`에 넣지 않는다. 값이 비어 있으면 잠김 사고 방지를 위한 통과 모드가 되므로
첫 배포 전에 secret 등록 여부를 확인한다. 버킷 Public URL은 켜지 않는다.

## 4. 배포 키와 HTTP 동작

`src/worker.js`가 허용하는 키:

```text
index.json
analysis-index.json
pre|bid/YYYY/MM/DD.csv.gz
pre|bid/YYYY/MM.csv.gz
analysis/bid/<슬래시 없는 1~160자>.json
```

`raw/`, `state/`, 첨부 및 변환 중간 산출물은 경로 정규식에서 차단된다. gzip 응답은
`Content-Type: application/gzip`으로 보내되 `Content-Encoding`은 붙이지 않는다. 브라우저가
`DecompressionStream("gzip")`으로 직접 해제하기 때문이다.

캐시 정책:

| 대상 | `Cache-Control` |
|---|---|
| `index.json`, `analysis-index.json` | `private, max-age=60` |
| 월별 봉인 gzip | `private, max-age=31536000, immutable` |
| 40일보다 오래된 일별 gzip | `private, max-age=31536000, immutable` |
| 최근 40일 일별 gzip | `private, max-age=300` |
| 기타 허용 JSON | `private, max-age=3600` |

R2의 ETag를 응답에 전달하고 요청 헤더를 `onlyIf` 조건으로 넘겨 조건부 요청 시 304를 반환한다.

## 5. 초기 배포 — 완료 (2026-08-09)

이 계획은 실행됐다. 실제 배포 상태와 단계별 명령·검증·사고 대응은
[워커-배포절차.md](워커-배포절차.md)가 기준 문서다. 이 절은 설계상 지켜야 할 조건만 남긴다.

| 조건 | 상태 |
|---|---|
| R2 버킷 `gong-go-data`의 Public URL이 꺼져 있을 것 | 유지 |
| `GATE_PASSWORD`는 설정 파일이 아니라 시크릿으로만 등록 | 유지 |
| 배포 후 **미인증** `/`와 `/app.js`가 401인지 가장 먼저 확인 | 확인함 |
| 인증 후 허용 R2 키·차단 경로·응답 헤더 검증 | 미완 (절차서 7장) |
| GitHub에 `SERVICE_KEY`와 업로더용 R2 자격증명 3개 등록 | 별도 확인 필요 |

> 시크릿이 **빈 문자열**이면 `src/worker.js`가 통과 모드로 떨어져 사이트 전체가 무인증으로
> 열린다. 실제로 그렇게 5분간 공개된 사고가 있었다. 등록 성공 메시지가 아니라 미인증 401로
> 확인해야 한다. 경위와 복구 절차는 절차서 11장에 있다.

`--prune`은 봉인 결과를 검증한 뒤에만 실행한다. 업로드 전에 정리하면 대체될 일별 파일을 다시
올리지 않아 초기 업로드가 작아진다. 원본 복구 경로인 `data/raw/`는 삭제하지 않는다.

## 6. 일일 자동화

워크플로는 `.github/workflows/collect.yml`에 구현되어 있다.

- 매일 UTC 20:00, KST 05:00 실행
- 수동 실행 시 `begin`, `end` 입력 가능
- 기본 범위는 UTC 기준 최근 35일 ~ 오늘
- `contents: read` 권한만 사용하며 저장소에 데이터 커밋을 만들지 않음
- 동시 실행은 `collect` 그룹에서 직렬화
- 제한 시간 60분
- 오류 로그는 14일간 artifact로 보관

GitHub의 `schedule`은 기본 브랜치에 존재하는 워크플로만 트리거한다. 따라서 실제 기본 브랜치가
`main`이라면 이 파일이 `main`에도 존재하고, 잡 내부에서 `ref: dev`를 체크아웃하는지 확인한다.

자동화 순서:

1. `uploader/upload.js --pull-state`
2. `collector/collector.js --no-resume`
3. `data/sync-errors.json`이 비어 있는지 검사
4. 같은 `SYNC_BEGIN`·`SYNC_END`로 `uploader/upload.js`

수집 작업 하나라도 실패하면 업로드 전에 중단한다. 부분 수집 파일이 R2의 정상 파일을 덮어쓰는
것을 막기 위한 절차다.

## 7. 업로더의 안전 규칙

업로더는 버킷 키와 ETag를 나열하고 로컬 MD5와 비교해 달라진 객체만 PUT한다. 별도 업로드 상태
파일은 사용하지 않는다.

데이터 반영 순서:

1. 일별·월별 CSV gzip 업로드
2. 로컬과 원격 인덱스를 병합한 `index.json` 업로드
3. 월 파일로 대체됐거나 명시된 수집 구간에서 사라진 일별 키 삭제
4. 분석 JSON과 `analysis-index.json` 업로드
5. `state/sync-state.json` 업로드

현재 분석 JSON과 분석 인덱스는 마지막 단계에서 같은 동시 업로드 배치로 처리된다. 데이터
`index.json`처럼 파일과 목록 사이의 엄격한 게시 순서는 보장하지 않으므로, ECR 분석 결과를 대량
배포할 때는 일시적으로 인덱스가 먼저 보일 수 있음을 운영상 유의한다.

삭제는 다음 두 경우만 허용된다.

- 버킷에 같은 달의 월별 봉인 키가 있을 때 그 달의 일별 키 삭제
- `SYNC_BEGIN`~`SYNC_END` 안에서 로컬 수집 결과에 사라진 일별 키 삭제

수집 구간 밖의 원격 키와 `state/`, `raw/`, `analysis/`는 일반적인 “로컬에 없음”만으로 삭제하지
않는다. 최근 구간만 가진 Actions 러너가 과거 데이터를 지우지 않게 하는 핵심 규칙이다.

## 8. 월별 봉인 운영

전체 데이터가 있는 로컬 환경에서 월 1회 실행한다.

```powershell
npm run compact -- --dry-run
npm run compact
npm run serve                    # 봉인 전후 조회 건수 확인
npm test
npm run compact -- --prune
npm run upload -- --dry-run
npm run upload
```

기본 봉인 지연은 40일이며 `--lag=<일수>`로 바꿀 수 있다. `--reseal`은 이미 존재하는 월 파일을
일별 원본으로 다시 만들 때 사용한다.

compact는 다음을 보장한다.

- 날짜순으로 병합하고 BOM·헤더를 한 번만 기록
- 헤더가 다른 일별 파일은 CSV를 다시 직렬화해 컬럼을 통합
- 병합 전후 행 수 불일치 시 해당 월을 건너뜀
- 기존 인덱스 또는 월 파일보다 행 수가 줄면 덮어쓰지 않음
- 기본 실행은 일별 원본을 남기며 `--prune`에서만 삭제
- 일별·월별 항목이 함께 있을 때 인덱스에는 월별 항목만 노출

## 9. 검증 체크리스트

### 저장소

```powershell
npm test
node --check uploader/upload.js
node --check collector/compact.js
node --check src/worker.js
npx wrangler deploy --dry-run
git status --short
```

### 배포 후

- 시크릿 창에서 `/` 접속 시 401 로그인 화면이 표시되는가
- 인증 없이 `/app.js`를 직접 요청해도 401인가 (`assets.run_worker_first` 실증)
- 인증 없이 `/data/index.json`을 직접 열어도 게이트가 적용되는가
- `/data/raw/...`와 `/data/state/sync-state.json`이 404인가
- gzip 응답에 `Content-Type: application/gzip`이 있고 `Content-Encoding`은 없는가
- 과거 월 파일에 `private, max-age=31536000, immutable`이 적용되는가
- 사전공고·본공고 조회, 기관 필터, 첨부 모달, CSV 다운로드가 동작하는가
- 분석 데이터가 있을 때 ECR 탭과 ECR CSV 다운로드가 동작하는가
- `workflow_dispatch` 실행 후 Worker 재배포 없이 새 인덱스가 조회되는가

## 10. 장애 대응과 롤백

- 수집 실패: artifact의 `sync-errors.json`을 확인하고 같은 범위로 수동 재실행한다.
- 잘못된 봉인: `data/raw/` 또는 남겨 둔 일별 파일로 `--reseal`한다. 검증 전에는 `--prune`하지 않는다.
- 잘못된 업로드: 업로드 순서를 재실행하고 `index.json`이 실제 R2 키를 가리키는지 확인한다.
- 게이트 장애: `GATE_PASSWORD`를 제거하면 통과 모드가 되므로 긴급 조치 시 데이터 공개 위험을
  함께 판단한다.
- R2 중단: [배포계획.md](배포계획.md)의 Git-정적 대안으로 전환한다.

Cloudflare의 요금과 무료 한도는 문서에 고정값으로 가정하지 않는다. 실제 요청량·저장량과 현재
플랜 한도를 대시보드에서 확인한 뒤 캐시 정책, 조회 범위 제한 또는 유료 플랜을 결정한다.
