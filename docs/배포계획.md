# dev 브랜치 배포 계획

`dev` 브랜치(수집 파이프라인 + CSV/ECR 뷰어)를 Cloudflare Pages에 올려 여러 사람이 브라우저로 접근할 수 있게 하는 계획.

- **저장**: gzip 데이터를 Git에 커밋 → Pages가 정적 파일로 서빙
- **수집**: GitHub Actions 크론(매일 자동) → 바뀐 gzip만 커밋 → Pages 자동 재배포
- **대상**: 운영 중인 `gong-go.pages.dev`(`main`)와 **별도 Pages 프로젝트** (예: `gong-go-archive`, 프로덕션 브랜치 `dev`)

> **개정 이력.** 최초 판(2026-07-20)은 데이터를 R2에 두는 안이었다. 그 뒤 수집기가 날짜별
> 파일을 `.csv.gz`로 저장하도록 바뀌면서 R2·바인딩·업로드 스크립트가 과설계가 되었고,
> 2026-07-21에 Git-정적 방식으로 개정하는 안이 나왔으나 병합되지 않은 채 남았다
> (`claude/session-8l3r8w`). 이 문서는 그 개정안을 현재 루트 구조와 브랜치 분리에 맞춰
> 반영한 것이다. R2는 규모가 커질 때의 대안으로 8장에 남겨 둔다.

## 1. 현재 구조

`main`과 `dev`는 `fcd3337`에서 갈라진 형제 브랜치이며, 서로의 파일을 공유하지 않는다.

| 브랜치 | 구성 | 역할 | 실행 환경 |
|---|---|---|---|
| `main` | `index.html`·`app.js`·`config.js`·`style.css`·`functions/` | 나라장터 API 실시간 조회 앱 | Pages + Functions (배포 완료) |
| `dev` | `collector/` | 공공데이터 API 수집 → 날짜별 `.csv.gz` | 로컬 Node / GitHub Actions |
| `dev` | `downloader/`·`converter/`·`analyzer/` | 첨부 다운로드 → 문서 변환 → ECR 추출 | 로컬 Node |
| `dev` | `public/` | 수집 데이터·ECR 뷰어 | 로컬 정적 서버 / Pages |
| `dev` | `data/` | 모든 단계의 입출력 (현재 gitignore) | — |

두 앱은 완전히 분리되어 있다. `main` 앱은 API를 실시간 프록시하고, `dev`는 미리 수집한 `.csv.gz`를 읽는다.

### 이미 끝나 있는 것

이전 계획서가 "1단계 — 슬림 출력 추가"로 잡았던 전송량 문제는 상당 부분 gzip으로 해소됐다.

- 날짜별 파일을 `.csv.gz`로 압축 저장(`549eb6d`, `1a204c8`).
- 프론트가 `DecompressionStream("gzip")`으로 브라우저에서 직접 해제(`public/app.js:26`).
- 파이프라인이 단계별 폴더로 분리되고 산출물이 `data/` 한 곳에 모임(`fcd3337`).
- ECR 추출 결과가 뷰어 모달에 연동됨(`6c7410c`) — **배포 대상이 CSV만이 아니다**(3장).

### 배포를 막는 세 가지

| 막는 것 | 현재 상태 | 해소 방법 |
|---|---|---|
| 데이터가 Git에 없다 | `.gitignore`가 `data/`를 통째로 제외 | 상태 파일만 제외하도록 좁힌다 (5-1) |
| 프론트 경로가 로컬 전용 | `DATA_BASE = "../data"`, `file:` 분기와 로컬 안내 문구 | `/data`로 바꾼다 (5-3) |
| 접근 통제가 없다 | 게이트는 `main`의 `functions/_middleware.js`뿐 | `dev`로 복사한다 (5-4) |

세 가지 모두 **아직 코드에 반영되지 않았다.** 개정안을 담은 브랜치가 병합되지 않았고, 그 브랜치는 폴더 분리 이전 구조(`../collector/data`)를 기준으로 하고 있어 그대로 가져올 수도 없다.

## 2. 규모 — 방식을 가르는 숫자

Git-정적이냐 R2냐는 전적으로 데이터 크기에서 갈린다. **배포 착수 전에 반드시 재측정한다.**

```powershell
node collector/collector.js          # 원하는 범위까지 수집한 뒤
du -sh data/pre data/bid data/analysis
find data/pre data/bid -name "*.csv.gz" | wc -l
```

### 기존 실측과 그로부터의 추정

최초 계획서의 실측치(`data/bid/2025/01/06.csv`: 원본 3.0 MB → gzip 279 KB, 압축비 약 10.7:1)와
"24일치 원본 86 MB"를 결합하면 gzip 기준 하루 약 0.33 MB다. `sync.config.json`의 범위가
`2025-01-01 ~ 오늘`이므로 전 구간은 약 575일이고, 따라서

| 항목 | 추정 |
|---|---|
| gzip 총량 (pre+bid 전 구간) | **약 190 MB** |
| 파일 수 | 약 1,150개 (575일 × 2) + `analysis/` |

**개정안이 근거로 삼은 "총 수십 MB"는 24일치 스냅샷 기준이었다.** 전 구간은 그보다 한 자릿수 크다.
그래도 아래 한도 안에는 들어가므로 Git-정적 방식은 여전히 성립한다.

| 한도 | 값 | 추정치 대비 |
|---|---|---|
| Pages 파일 수 (Free) | 20,000 | 약 1,150 — 여유 |
| Pages 파일 크기 | 25 MiB | 파일당 1 MB 미만 — 여유 |
| Pages 빌드 | 500회/월 | 하루 1회 — 여유 |
| Pages 이그레스 | 무료 | — |
| GitHub 저장소 권장 상한 | 1 GB (경고 기준) | 약 190 MB — 여유는 있으나 유일한 압박점 |

**판단 기준:** 재측정 결과가 **500 MB 미만이면 Git-정적**으로 간다. 그 이상이면 8장의 R2 전환을 먼저 검토한다.

초기 전 구간 적재가 한 번에 190 MB짜리 커밋이 되는 점은 감수한다. 이후 일일 증분은
과거 날짜가 불변이라 최근 며칠분 몇 개 파일에 그친다.

## 3. 배포 대상 — CSV만이 아니다

프론트가 `DATA_BASE` 아래에서 실제로 요청하는 것은 네 종류다(`public/app.js`).

| 경로 | 내용 | 생성 단계 |
|---|---|---|
| `index.json` | 날짜별 CSV 파일 목록 | collector |
| `{pre,bid}/YYYY/MM/DD.csv.gz` | 날짜별 공고 | collector |
| `analysis-index.json` | ECR 분석 인덱스 | analyzer |
| `analysis/bid/<공고번호>.json` | ECR 추출 결과 | analyzer |

이전 계획서는 앞의 두 가지만 다뤘다. ECR 연동(`6c7410c`)이 그 뒤에 들어왔으므로 **`analysis-index.json`과 `analysis/`도 함께 배포해야** 모달의 ECR 탭이 동작한다. 없으면 뷰어는 조용히 "분석된 ECR 규격이 없습니다"로 표시된다.

반대로 `files/`(원본 첨부), `norm/`, `text/`(변환 중간 산출물)는 **배포 대상이 아니다.** 용량이 가장 크고 뷰어가 읽지 않는다. 크론도 이 단계들을 돌리지 않는다 — 첨부 다운로드·변환·ECR 추출은 당분간 로컬에서 수동 실행하고 결과만 커밋한다.

## 4. 목표 아키텍처

```
GitHub Actions 크론 (매일 KST 05:00, main에서 실행 — 6장 참조)
  └ dev 체크아웃 → node collector/collector.js   SYNC_BEGIN으로 최근 35일만
     └ 바뀐 data/{pre,bid}/**.csv.gz + index.json 만 dev에 커밋·푸시
        └ Cloudflare Pages (dev 푸시 시 자동 빌드)
           빌드: bash build.sh   →  data/ 에서 배포 대상만 public/data/ 로 복사
           출력: public
           ├ functions/_middleware.js   비밀번호 게이트 (main에서 복사)
           ├ /data/index.json, /data/{pre,bid}/**.csv.gz
           ├ /data/analysis-index.json, /data/analysis/bid/*.json
           └ index.html / app.js / style.css
```

게이트가 모든 요청보다 먼저 실행되므로 `/data/**`도 자동으로 게이트 뒤에 놓인다.

## 5. 단계별 실행

**전부 미착수다.** 각 단계 끝에 검증 방법을 적는다.

### 5-1. 데이터를 배포 대상으로 편입

`.gitignore`를 `data/` 통째 제외에서 상태 파일 제외로 좁힌다.

```
.env
rfp_sample/

# 상태·중간 산출물은 제외, 배포 대상 gzip/JSON만 추적
data/sync-state.json
data/sync-errors.json
data/analysis-state.json
data/files/
data/norm/
data/text/

public/data/          # build.sh 산출물, 커밋 대상 아님
```

**검증:** `git status --short data/` 에 `pre/`·`bid/`·`analysis/`·`index.json`만 올라오는지 확인.

### 5-2. 빌드 시 `/data` 서빙 — `build.sh`

데이터가 출력 디렉터리(`public`) 밖에 있으므로 빌드 때 복사한다. 3장의 배포 대상만 골라 담는다(`files/`·`norm/`·`text/` 제외).

Pages 설정: 빌드 명령 `bash build.sh`, 출력 디렉터리 `public`.

**검증 — 가장 놓치기 쉬운 지점:** `.csv.gz`는 Pages가 **`Content-Encoding` 없이 원본 바이트로** 서빙해야 한다. 프론트가 `DecompressionStream`으로 직접 해제하므로, Pages가 자동 해제하거나 `Content-Encoding: gzip`을 붙이면 이중 처리로 깨진다. 배포 후 `curl -I`로 `/data/bid/2025/01/06.csv.gz` 헤더를 한 번 확인한다.

### 5-3. 프론트 경로 정리

`public/app.js`:

- `DATA_BASE` `"../data"` → `"/data"`
- `file:` 분기의 `C:\gong-go에서 python -m http.server...` 안내를 배포용 문구로 교체

**검증:** 로컬에서도 `public/`을 루트로 서빙하면 `/data`가 맞아야 하므로, 로컬 실행법이 바뀐다. README 갱신이 따라온다.

### 5-4. 게이트 이식

`main`의 `functions/_middleware.js`를 `dev`의 `functions/_middleware.js`로 복사한다. 수정 없이 그대로 쓴다 — 두 파일이 갈라지지 않도록 변경이 필요하면 양쪽에 함께 반영한다.

`GATE_PASSWORD`가 비어 있으면 게이트가 통과 모드로 동작하므로(`_middleware.js`의 잠김 방지 설계), **환경변수 설정 전까지 데이터가 공개된다.** 7장 순서를 지킨다.

**검증:** 배포 후 시크릿 창으로 접속해 로그인 화면이 뜨는지, `/data/index.json`을 직접 열어도 막히는지 확인.

### 5-5. 수집기에 실행 범위 오버라이드 추가

크론 러너는 `sync-state.json`을 커밋하지 않으므로 매번 resume 상태 없이 시작한다. 그대로 두면 전 구간을 매일 재수집한다. `collector/collector.js:55`를 환경변수 우선으로 바꾼다.

```js
const begin = parseDate(process.env.SYNC_BEGIN || config.begin || "2015-01-01");
const end = parseDate(process.env.SYNC_END || config.end || today());
```

`sync.config.json`은 러너에서 건드리지 않는다.

**검증:** `SYNC_BEGIN=2026-07-01 node collector/collector.js --dry-run` 으로 범위가 좁아지는지 확인.

## 6. GitHub Actions 크론 — 브랜치 제약이 핵심

`.github/workflows/collect.yml`을 새로 만든다. 다만 **워크플로 파일을 `dev`에 두면 크론이 돌지 않는다.**

> GitHub Actions의 `on: schedule`은 **기본 브랜치의 워크플로 파일만** 트리거한다. 기본 브랜치가 `main`이므로, `dev`에만 있는 워크플로는 스케줄로 실행되지 않는다.

따라서 이렇게 구성한다.

- 워크플로 파일은 **`main`에 둔다.**
- 잡에서 `actions/checkout@v4`로 **`ref: dev`를 체크아웃**하고, 수집 후 **`dev`로 커밋·푸시**한다.
- Pages 프로젝트(`gong-go-archive`)의 프로덕션 브랜치가 `dev`이므로 그 푸시가 재배포를 트리거한다.

`main`에 `.github/`가 생기는 것이 `main`의 Pages 배포에 영향을 주는지는 배포 후 확인한다(점으로 시작하는 디렉터리는 정적 자산에서 제외되는 것이 일반적이지만, 확인 없이 단정하지 않는다). 노출된다면 `main`의 게이트 뒤에 있기는 하다.

워크플로 내용:

```yaml
on:
  schedule:
    - cron: "0 20 * * *"   # UTC 20:00 = KST 05:00
  workflow_dispatch:
    inputs:
      begin: { description: "수집 시작일(YYYY-MM-DD). 비우면 최근 35일.", default: "" }
      end:   { description: "수집 종료일(YYYY-MM-DD). 비우면 오늘.",      default: "" }
```

- Node 20 → `node collector/collector.js` → 바뀐 `data/**` 만 `dev`에 커밋·푸시
- **범위:** `SYNC_BEGIN`으로 최근 35일. 과거 날짜는 이미 커밋된 gzip을 승계한다
- **빈 빌드 방지:** 변경이 없으면 커밋 생략(`git diff --cached --quiet`)
- **실패 처리:** `sync-errors.json`이 비어있지 않으면 워크플로 실패
- **Secret:** `SERVICE_KEY` 하나

**검증:** `workflow_dispatch`로 1회 수동 실행해 `dev`에 커밋이 생기고 Pages가 재배포되는지 확인한 뒤 크론을 켠다.

## 7. 남은 작업 (대시보드 · 시크릿)

코드 커밋만으로는 끝나지 않는다. **순서를 지킨다** — 3번 전에 2번을 해야 데이터가 무방비로 공개되지 않는다.

1. Cloudflare Pages 새 프로젝트 `gong-go-archive` 생성 → 저장소 연결
   - 프로덕션 브랜치 `dev`, 빌드 명령 `bash build.sh`, 출력 디렉터리 `public`
   - 프리뷰 브랜치는 `None`으로 둔다
2. 환경변수 `GATE_PASSWORD` 설정 — **Production과 Preview 양쪽 모두.** 한쪽만 설정하면 그쪽은 게이트가 꺼진 채 배포된다
3. GitHub 시크릿 `SERVICE_KEY` 등록
4. 초기 전 구간 적재: `collect`를 `workflow_dispatch`로 1회 실행(`begin=2025-01-01`)
5. 배포 검증: 게이트 → 목록 → 첨부 모달 → ECR 탭 → CSV 다운로드, 그리고 5-2의 gzip 헤더 확인

`main`의 기존 `gong-go` 프로젝트는 프리뷰 브랜치를 `main`으로 제한해 두었다. `dev` 푸시가 그 프로젝트를 건드리지 않는다.

## 8. 보안 점검

| 항목 | 상태 |
|---|---|
| `.env` Git 커밋 이력 | 없음 (`.gitignore`로 제외) |
| 상태 파일 추적 | `sync-state.json`·`sync-errors.json` 등 제외, 배포 대상만 추적 |
| `SERVICE_KEY` | Actions Secret으로만 주입, 클라이언트 노출 없음 |
| 데이터 접근 통제 | `_middleware.js` 공유 비밀번호 게이트(정적 `/data`도 게이트 뒤) |
| 커밋 데이터 민감도 | 공공데이터 공개 공고 정보 — 개인정보 아님 |
| 첨부 원문(`files/`) | 커밋하지 않음 — 저작권·용량 양쪽 이유 |

게이트는 단일 공유 암호라 유출 시 개인별 차단이 불가능하다. 사용자가 늘거나 데이터 민감도가 올라가면 Cloudflare Access(SSO)로 교체를 검토한다.

## 9. 대안 — R2로 전환하는 기준

Git-정적 방식의 약점은 **저장소 히스토리 비대화**다. 2장의 재측정치가 500 MB를 넘거나, 매일 커밋이 쌓여 클론·빌드가 눈에 띄게 느려지면 R2로 옮긴다.

- R2 버킷 `gong-go-data` 생성, 공개 접근 비활성화
- 6장의 "커밋" 대신 `uploader/upload.js`로 변경된 날짜만 PUT(로컬 해시 캐시로 무변경 건너뛰기). `sync-state.json`도 R2에 왕복 보관해 증분 상태를 유지한다
- 5-2의 정적 복사 대신 `functions/data/[[path]].js`로 R2 바인딩(`DATA`)을 중계하고, 키 정규식으로 경로를 제한한다

```js
export async function onRequestGet({ env, params }) {
  const key = params.path.join("/");
  if (!/^(index\.json|analysis-index\.json|(pre|bid)\/\d{4}\/\d{2}\/\d{2}\.csv\.gz|analysis\/bid\/[\w-]+\.json)$/.test(key))
    return new Response("Not found", { status: 404 });
  const obj = await env.DATA.get(key);
  if (!obj) return new Response("Not found", { status: 404 });
  return new Response(obj.body, {
    headers: {
      "Content-Type": key.endsWith(".json") ? "application/json; charset=utf-8" : "application/gzip",
      "Cache-Control": key.endsWith(".json") ? "public, max-age=300" : "public, max-age=86400",
    },
  });
}
```

R2 무료 한도(저장 10 GB, 이그레스 무료)면 수년치도 월 $0이다. 지금 규모에서는 과설계이므로 필요해질 때 전환한다.

## 10. 조회 UX 보완 (선택, 데이터가 커진 뒤)

gzip 이후에도 넓은 범위 조회는 무겁다. 필요해지면 싼 것부터:

- 조회 범위 상한을 UI에서 제한(예: 최대 31일)
- 파일 단위 순차 로딩 + 진행률 표시(현재 `public/app.js:13`은 `Promise.all` 동시 요청)
- 컬럼 화이트리스트 투영으로 파싱 부하 감소(원본은 로컬에 두고 배포본만 슬림화)
- 그래도 부족하면 D1로 이전해 서버측 필터링

지금 미리 할 필요는 없다. 실제 사용 패턴을 보고 판단한다.
