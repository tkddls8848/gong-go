# 관심사업 저장과 진행 상태·개찰결과 추적 — 설계

2026-11-26 · 상태: 사용자 승인 범위 구현·단계별 독립 검토 완료 (`feature/tracked-businesses`, 운영 배포 전)

## 왜

참여하려는 사업을 저장해 두고, 다시 볼 때 **지금 어느 단계인지, 다음 일정이 언제인지, 개찰됐으면 결과가 어떤지**를 공고를 하나씩 검색하지 않고 한곳에서 빠르게 확인한다. 사업은 공고 하나로 끝나지 않는다 — 유찰되면 재공고(2차 공고), 다시 유찰되면 수의계약으로 이어진다. **저장한 것은 공고 한 건이 아니라 사업이고, 그 사업의 다음 공고까지 따라가야 한다**(사용자 요구).

## 목표

- 본공고 행과 **사전공고(사전규격) 행**을 관심사업으로 저장·해제한다.
- 사전공고로 저장한 사업은 감시하다가 그 사전규격에서 본공고가 나오면 **자동으로 본공고와 잇고** 이후는 본공고와 똑같이 추적한다(사용자 요구).
- 관심사업 목록에서 사업마다 현재 단계와 다음 일정을 한 줄로 본다.
  - 사전규격 단계: "사전규격 공개 · 의견등록 마감 D-n", 마감 뒤에는 "본공고 대기".
  - 공고 전·개찰 전: 일정 기준 단계와 D-day(예: "입찰 마감 D-3", "개찰 대기").
  - 개찰 후: 개찰완료 / 유찰 / 재입찰. 유찰 뒤 재공고·수의계약 공고가 나오면 **자동으로 그 공고를 현재 공고로 삼는다.**
- 사업의 공고 이력(1차 → 재공고 → 수의계약)을 순서대로 본다.
- 유찰이면 유찰사유를 본다.
- 개찰완료면 참여업체별 순위·업체명·투찰금액·투찰률·비고, 평가점수가 있는 공고(협상에 의한 계약 등)는 **기술·가격·종합 평가점수**도 본다.
- 수의계약 공고는 낙찰(계약상대) 업체 정보를 본다.

## 비목표

- 공개 API가 제공하지 않는 값(사용자 결정: 제공되지 않는 데이터는 구현하지 않는다).
- 사전규격·발주계획 번호가 없는 공고의 재공고 연결 — API가 연결 키를 주지 않는다. 이런 사업은 "저장한 공고만 추적"으로 표시한다.
- 기기 간 목록 동기화, 서버 저장(사용자가 브라우저 저장을 골랐다).
- 알림(메일·푸시), 주기적 자동 조회.
- 전체 공고의 개찰결과 수집·검색, 수집기·CSV 계약 변경.

## 반목표(돌아가도 실패인 것)

- 조회 실패·키 미승인을 "결과 없음"·"개찰 전"·"재공고 없음"으로 보이는 것. 실패는 실패로, 해야 할 일과 함께 보인다.
- 연결 키가 없어 재공고를 못 찾는 사업을 "재공고 없음"으로 단정하는 것.
- 관심사업 화면을 여는 것만으로 공공 API 일일 한도를 크게 깎는 것.
- 내부 오류 문구·상류 원문 오류를 화면에 노출하는 것.

## 제약

## 확인한 API 사실 (2026-11-26 실제 호출, 포털 명세에 일부 없음)

**계약과정통합공개서비스** `getCntrctProcssIntgOpen{Thng,Servc,Cnstwk,Frgcpt}` — 업무구분별.

- `inqryDiv=1`+`bidNtceNo`, `inqryDiv=2`+`bfSpecRgstNo`, `inqryDiv=3`+`orderPlanNo`가 동작한다.
- 공고번호로 부르면 그 공고의 `bfSpecRgstNo`·`orderPlanNo`가 나온다(없으면 빈 값 — 예 R26BK01832601).
- 사전규격번호로 부르면 같은 사업의 공고가 모두 나온다. 예 R26BD00278954 → R26BK01756351(1차, 일반경쟁, 10-07) · R26BK01779016(재공고, 일반경쟁, 10-19, 유찰) · R26BK01847773(수의계약, 전자시담, 11-23). 차수가 다른 행(정정공고)도 따로 나온다(예 R26BK01410643 000·001).
- 행 필드: `bidNtceNo`, `bidNtceOrd`, `bidNtceNm`, `bidNtceDt`, `cntrctCnclsMthdNm`(일반경쟁·수의계약…), `bidMthdNm`(전자입찰·전자시담…), `bidwinrInfoList`, `cntrctInfoList`, 사전규격·발주계획 정보.
- `bidwinrInfoList` 예: `[1^모아맘보육재단^2208264545^김광자^830575896^97.001^1^2026-11-23 12:30:00]` — 순위^업체명^사업자번호^대표자^금액^비율^?^일시로 보인다. 여러 건 구분자는 표본이 없어 미확인(빌더가 방어적으로 파싱).

**낙찰정보서비스** `/1230000/as/ScsbidInfoService`

| 쓰임 | 오퍼레이션 | 인자 | 쓰는 출력 |

| 개찰 진행 상태 | `getOpengResultListInfo{Thng,Servc,Cnstwk,Frgcpt}` | `inqryDiv=4`, `bidNtceNo` | `bidNtceOrd`, `bidClsfcNo`, `rbidNo`, `opengDt`, `prtcptCnum`, `progrsDivCdNm`(개찰완료·유찰 확인), `opengRsltNtcCntnts` |

## 설계

### 저장 단위 = 사업

항목(localStorage `gong-go:tracked-businesses`, `{ version: 1, items: [...] }`):

- `savedFrom`: `"bid"` | `"pre"`, `savedNo`: 저장한 공고번호(본공고 번호 또는 사전규격등록번호)
- `chainKey`: `{ kind: "spec" | "plan", no }` — 사전공고로 저장하면 저장 때 `spec`으로 정해진다. 본공고로 저장하면 처음 조회에서 채운다. 둘 다 없으면 `null` = 저장 공고만 추적.
- `businessType`: 사전공고 행은 `bsnsDivNm`이 있어 저장 때 정해진다. 본공고는 처음 조회에서 채운다.
- 스냅숏: 공고명, 수요기관, 상세 URL, 본공고면 `bidSchedule`, 사전공고면 의견등록 마감(`opninRgstClseDt`) — CSV 없이 목록을 그리기 위해.
- `lastResult`: 마지막 조회 응답과 받은 시각.

중복 판정: 같은 `chainKey`이거나 같은 `savedNo`면 같은 사업이다(재공고 행을 또 저장하면 새 항목이 아니라 기존 사업을 알려 준다).

### Worker: `GET /api/business-status`

- 새 파일 `src/business-status.js`. `src/worker.js`에서 **게이트 뒤**(`/api/live`와 같은 자리)에 라우팅.
- 입력: `bidNtceNo` 또는 `specNo` 중 하나 이상(필수, 형식 검증), `businessType`(선택), `planNo`(선택). 사전공고로 저장한 사업은 `specNo`만으로 부른다.
- 처리:
  1. 연결 키를 모르면 통합공개를 `inqryDiv=1`로 부른다(업무구분 모르면 최대 4회, 첫 적중에서 멈춤) → `bfSpecRgstNo`·`orderPlanNo`.
  2. 연결 키가 있으면 통합공개를 `inqryDiv=2`(사전규격 우선) 또는 `3`으로 불러 사업의 공고 목록을 얻는다. 없으면 저장 공고 하나만 목록으로 삼는다.
  - 사전규격으로 부른 응답에서 `bidNtceNo`가 빈 행(아직 본공고 없음)은 공고로 치지 않는다. 공고가 하나도 없으면 `stage: "spec"`(본공고 전)으로 돌려준다 — 오류가 아니다. 이 응답 형태는 표본이 없어 빌더가 실제 응답으로 확인한다.
  3. 목록을 공고일시 순으로 정렬하고 같은 번호는 최신 차수만 남긴다. **현재 공고** = 가장 늦게 게시된 공고.
  4. 현재 공고와, 이전 공고 중 결과를 아직 모르는 것에 대해 낙찰정보를 부른다: 진행 상태 1회 → 유찰이면 유찰사유, 개찰완료면 업체별(페이지 상한), 재입찰이면 재입찰 사유. 이전 공고는 상태 요약만, 상세(업체 표)는 현재 공고만 받는다.
  5. 공고 수가 많으면 최근 8건까지만 본다.
  - 요청당 상류 호출 상한을 코드 상수로 두고 50 미만을 지킨다(테스트로 고정).
- 출력: 상류 원문이 아니라 정규화한 JSON.
  ```json
  { "businessType": "용역", "chainKey": { "kind": "spec", "no": "R26BD00278954" },
    "notices": [
      { "bidNtceNo": "R26BK01756351", "ord": "000", "postedAt": "...", "method": "일반경쟁", "bidMethod": "전자입찰", "state": "failed", "reason": "..." },
      { "bidNtceNo": "R26BK01779016", "...": "...", "state": "failed", "reason": "..." },
      { "bidNtceNo": "R26BK01847773", "method": "수의계약", "bidMethod": "전자시담", "state": "opened",
        "winners": [{ "rank": 1, "name": "모아맘보육재단", "amount": 830575896, "rate": 97.001 }] } ],
    "current": { "bidNtceNo": "R26BK01847773", "state": "opened", "openedAt": "...", "participants": 1, "notice": "...",
      "bidders": [{ "rank": 1, "name": "...", "bizno": "...", "amount": 0, "rate": 0, "remark": "...",
                   "techScore": null, "priceScore": null, "totalScore": null }] } }
  ```
  `state`: `before`(결과 행 없음) · `opened` · `failed` · `rebid`. 상류 오류·인증 실패·형식 불일치는 `before`나 빈 목록으로 바꾸지 않고 오류 응답(구분 가능한 코드 + 한국어 안내)으로 돌려준다. 연결 조회만 실패하고 결과 조회는 됐다면 "이어진 공고를 확인하지 못함" 표시를 담아 부분 성공으로 준다.
- 캐시: 성공 응답만 Worker Cache에 5분(src/live.js 방식). 쿠키·서비스 키는 캐시 키에 넣지 않는다. 브라우저에는 `no-store`.

### 브라우저: 관심사업 모듈

- 새 파일 `public/tracked.js` — 생성 함수(`createTracked({ storage, fetch, now, html, ... })`)로 상태와 의존성을 받는다. index.html 스크립트 목록에 추가하고 app.js가 조립한다.
- 저장 진입점: 본공고·사전공고 결과 행과 상세 모달에 저장 토글(☆/★). 발주계획 행에는 없다.
- 보기: 레일의 공고 유형 아래 **"관심사업 (n)"** 항목. 누르면 결과 표 자리에 관심사업 표가 보인다.
  ```
  관심사업 3건                                              [결과 새로 확인]
  사업명                  수요기관   현재 공고          상태                    결과
  ○○ 시스템 구축          국민연금   R26BK0123456      입찰 마감 D-3            -
  △△ 장비 구매            심평원     R26BK0120001      개찰완료 11/20           1위 ○○ 93.67점 · 4개사 ▸
  직장어린이집 위탁        국방연     R26BK01847773     수의계약 · 낙찰 11/23     모아맘보육재단 97.0% ▸
                                    (1차 유찰 → 재공고 유찰 → 수의계약)
  □□ 유지보수             건보공단   R26BK0119999      유찰 11/18 · 재공고 대기   단독응찰 ▸
  ```
  - 현재 공고가 저장한 공고와 다르면 이력 한 줄("1차 유찰 → 재공고 유찰 → 수의계약")을 보인다.
  - 연결 키가 없는 사업은 "사전규격·발주계획 연결 정보 없음 — 이 공고만 추적" 표시. 유찰돼도 "재공고 없음"이라 하지 않는다.
- 상세(▸): 공고 이력 표(번호·게시일·계약방법·상태·사유/낙찰자)와 현재 공고의 업체별 표. 점수 열은 응답에 점수가 있을 때만, 금액·투찰률 열은 값이 있을 때만 보인다. 행 펼침이나 모달 탭 중 기존 구조에 맞는 쪽은 빌더가 고른다.
- 조회 시점: 관심사업 보기를 열 때 **자동 조회 대상**만 조회한다.
  - 자동 대상: (0) 아직 본공고가 없는 사전공고 사업(본공고가 나왔는지 감시, 업무구분을 알아 1회 호출), (a) 현재 공고의 기준 시각(개찰 예정 `opengDt`, 없으면 입찰 마감 `bidClseDt`)이 지났고 개찰완료 결과를 아직 받지 않은 사업, (b) 마지막 상태가 유찰·재입찰인 사업(재공고·수의계약이 나올 수 있다), (c) 기준 시각이 없는 사업.
  - 저장 직후 1회 조회해 `chainKey`·`businessType`을 채운다.
  - "결과 새로 확인" 버튼은 모든 사업을 다시 조회한다(협상 계약은 개찰 뒤에도 결과가 바뀔 수 있다).
  - 일정은 현재 공고가 저장 공고와 같으면 스냅숏의 `bidSchedule`을, 다르면(재공고) 통합공개가 준 게시일과 결과만 보인다. 재공고의 입찰 일정은 그 공고를 검색해 저장 토글을 누르면 스냅숏이 갱신된다 — 별도 상류 호출 없음.
  - 동시 요청 수는 작게 제한한다.
- 실패 표시: 사업 단위로 "결과를 확인하지 못했습니다. 잠시 뒤 다시 확인하세요." / 권한 오류면 "낙찰·계약과정 조회 권한이 없습니다(서비스 키 활용신청 확인)". 실패한 사업을 "개찰 전"으로 보이지 않는다. 직전 결과가 있으면 받은 시각과 함께 그대로 둔다.

## 설계자가 정한 것(검토 바람)

- 사전규격번호가 있으면 그것으로, 없으면 발주계획번호로 사업을 잇는다.
- 저장은 본공고·사전공고 행에서 한다. 발주계획 행 저장은 이번 범위 밖(사용자가 요청하지 않음).
- 사전공고로 저장했다가 이어진 본공고 행을 또 저장하면 같은 사업으로 본다(같은 사전규격번호).
- 이전 공고는 상태·사유·낙찰자 요약만, 업체별 상세 표는 현재 공고만 받는다(호출 수 절약).
- 재공고의 입찰 일정은 별도 호출로 받지 않는다.
