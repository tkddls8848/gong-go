- 위치/함수: `src/ecr.js:13`, `55`의 `MAX_CHUNKS` / `splitDocument`, `src/ecr.js:165`, `171`, `176`, `213`, `219`, `232`의 `handleEcr`; `src/ai-budget.js:12`의 `reserveNeurons`.
- 재현 조건: 마지막 구간을 새로 추론하면서 N개 part를 병합하고, 예산 예약은 k번째 시도에 성공한다(1≤k≤6). 실제 모형에서 N=1, k=1의 R2 호출 8회를 확인했다.
- 계산: job GET 1 + part GET 1 + refine GET 1 + 예산 GET/PUT 2k + part PUT 1 + 병합 GET N + notice PUT 1 = **R2 N+5+2k회**. AI.run을 보수적으로 1회 더 세는 합산 모형은 **N+6+2k회**다. 사이트/AI 쿠키 검증은 로컬 crypto이므로 R2 호출 0회이며 잠금 해제 요청의 R2 호출은 별도 요청이다. 성공한 세분화 중간 단계는 병합 전에 반환하므로 한 HTTP 요청에 모델 호출이 여러 번 누적되지는 않는다.

| 조건 | R2 호출 | AI 1회를 합친 보수적 횟수 | 50회를 넘는 최소 N |
| --- | ---: | ---: | ---: |
| 새 추론, k=1 | N+7 | N+8 | R2만 44 / 합산 43 |
| 새 추론, k=2 | N+9 | N+10 | R2만 42 / 합산 41 |
| 새 추론, k=3 | N+11 | N+12 | R2만 40 / 합산 39 |
| 새 추론, k=6 | N+17 | N+18 | R2만 34 / 합산 33 |
| part가 이미 저장된 재병합 | N+3 | N+3 | 48 |

- 사용자 영향: **요청된 ‘전체 50회’ 가정에서는** MAX_CHUNKS=40이어도 세 번째 예약 시도 성공 시 51 R2 호출(합산 52), 여섯 번째면 57(합산 58)이다. 다만 실제 Workers Free는 외부 요청 50회와 내부 서비스 요청 1,000회를 구분한다([Workers limits](https://developers.cloudflare.com/workers/platform/limits/#subrequests), [2026-02-11 공식 변경 이력](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/)). 따라서 **현재 R2 바인딩의 40개 병합이 이 수치 때문에 실제 플랫폼 한도를 넘는다고 판정할 수 없다.** 구형 job은 업로드 시 splitDocument를 다시 통과하지 않으므로 40을 초과한 기존 chunks도 별도 고려해야 한다. 캐시 병합 N+3이 1,000을 넘는 최초 N은 998이지만, 그런 기존 작업이 실제 존재한다는 증거는 없다.
- 권장 수정: 주석·설계 근거를 내부/외부 호출 구분에 맞게 고치고 CAS 최악 횟수를 포함해 계산한다. 추론과 finalize를 분리하면 재병합은 N+3으로 고정된다. 기존 job의 크기 검증·분할 병합을 추가하되 40개 제한을 무조건 더 낮추는 조치는 근거가 부족하다. 50회 제한이 별도로 적용되는 구형 플랜/환경이라면 40개는 최악 경로를 보장하지 않으며, part 저장 후 병합만 재시도하면 43회로 복구 가능하다.

## (e) 인증/잠금

### E1 — 중간 · 확인: 잠금/로그아웃은 발급 토큰을 서버에서 취소하지 않음

- 위치/함수: `src/ai-access.js:13`의 `hasAiAccess`, `src/ai-access.js:52`의 `handleAiAccess`; `src/worker.js:96`의 `fetch`, `src/worker.js:545`의 `isAuthenticated` / `577`의 `tokenFor`.
- 재현 조건: 정상 로그인한 클라이언트가 사이트 쿠키와 AI 쿠키를 보관한 뒤 DELETE /api/ai-access 또는 사이트 로그아웃을 실행하고, 보관한 쿠키로 동일 Origin의 step을 재전송한다. 쿠키 삭제는 브라우저 저장소만 바꾸고 서버 검증 상태에는 영향을 주지 않는다. AI 토큰은 서명·만료만 확인하며 사이트 토큰은 비밀번호에서 결정적으로 생성된다.
- 사용자 영향: ‘잠금’ 이후에도 보관된 AI 토큰은 남은 30분 유효기간 내 재사용 가능하다. 이는 유효 자격 재사용이며 비밀번호 없이 새 토큰을 만드는 우회는 아니다. 로그아웃을 서버 측 즉시 권한 회수로 기대하는 경우에 문제가 된다.
- 권장 수정: 즉시 회수가 제품 요구라면 세션/토큰 nonce 폐기 또는 사용자별 권한 epoch를 서버에서 검사한다. 공유 비밀번호 기반 사이트 쿠키와 AI 토큰의 연결도 명시한다. 브라우저 한정 잠금이 의도라면 재사용 유효기간을 명확하게 안내한다.

### E2 — 중간 · 확인: 공유 전역 시도 한도를 사이트 사용자만으로 소진 가능

- 위치/함수: `src/ai-access.js:25`, `55`~`62`의 `attemptLimit` / `handleAiAccess`.
- 재현 조건: 사이트 게이트를 통과한 사용자가 10개 IP에서 각 5회 잘못된 잠금 해제 요청을 보낸다. 잘못된 본문과 성공한 인증도 검사 전에 시도 수에 포함된다. 10분 window 전역 50회가 소진되면 새 IP의 올바른 비밀번호도 거절된다.
- 사용자 영향: 다른 정상 사용자가 최대 해당 window 종료까지 429로 잠금을 풀 수 없다. 인증을 얻는 우회는 아니며 가용성 문제다. 기존 AI 쿠키가 유효한 사용자의 step은 이 카운터를 거치지 않는다.
- 권장 수정: 사이트 세션별·IP별 제한과 전역 방어의 정책을 나누고, 정상 운영자 복구 수단을 둔다. 정확한 남은 window에 맞는 Retry-After를 제공한다. 게이트 계정이 공유되는 구조에서는 공격자 구분의 한계도 고려한다.

### E3 — 낮음 · 확인: 허용된 비밀번호 설정 중 입력으로 제출 불가능한 길이 존재

- 위치/함수: `src/ai-access.js:5`의 `configured`, `src/ai-access.js:37`의 `passwordBody`, `src/ai-access.js:62`의 `handleAiAccess`.
- 재현 조건: AI_ANALYSIS_PASSWORD를 ASCII 513자로 설정한다. configured는 true지만 모든 제출을 512자 제한에서 거절한다. 512자 이내라도 JSON escape로 표현되는 제어문자가 많으면 2,048바이트 본문 제한에 걸릴 수 있다.
- 사용자 영향: 운영자에게는 설정됨으로 표시되지만 정확한 암호로도 새 AI 쿠키를 발급받을 수 없다. 일반적인 16~수십 자 비밀번호에서는 발생하지 않는다.
- 권장 수정: 설정 검증과 입력 제한을 통일하고 배포 시 검증한다. 지원하지 않는 secret은 설정 오류로 분명히 알린다.

**경로 순서 확인:** `worker.fetch`의 사이트 게이트 검사(`src/worker.js:106`)를 통과해야 `routeRequest`의 /api/ecr 및 /api/ai-access(`182`~`183`)에 도달한다. gate 앞 relay·robots·login·logout 분기는 ECR 실행 경로로 이어지지 않는다. `wrangler.jsonc`의 run_worker_first도 true다. ECR POST는 Origin 확인(`src/ecr.js:128`)과 requireAiAccess(`130`) 뒤에 업로드·PDF 변환·예약·추론을 실행한다. 사이트 쿠키만으로 유료 작업을 시작하는 순서 우회는 발견하지 못했다.

GET /api/ecr는 AI 잠금보다 먼저 저장 결과를 반환한다(`src/ecr.js:120`의 `handleEcr`). 이는 사이트 조회 권한과 뉴런 사용 권한을 분리한다는 `src/ai-access.js:1`의 의도에 맞으며, **‘모든 ECR 읽기도 AI 잠금 필요’ 정책이라면 추가해야 할 검사**다. /api/ai-access는 잠금을 풀기 위한 API이므로 기존 AI 쿠키를 요구하지 않되, POST는 Origin·비밀번호·시도 제한을 검사하고 GET은 상태만 공개한다. /data 경로는 `src/worker.js:50`의 KEY 허용 목록으로 `_ecr` 및 `_meta` 직접 조회를 허용하지 않는다. 외부에 R2 버킷을 별도 공개했는지는 이 코드만으로 검증하지 않았다.
